지금까지 확정된 것 (요약)

  • 대상: 최신 데스크톱 + 모바일 브라우저. 초당 수천 건 이상. 목표 수치는 성능 목표 참고.
  • 탭마다 Dedicated Worker가 sync access handle로 자기 세그먼트에 씁니다. SharedWorker는 쓰지 않습니다.
  • 여러 탭 중 하나만 해야 하는 일(보존 정리, 업로드, 주인 없는 파일 복구)은 Web Locks로 조율합니다. 업로드와 보존 정리 Lock은 실행할 때만 잡고 바로 놓습니다. 탭 상태에 따른 조건은 없습니다(#022).
  • 업로드는 사용자가 넘기는 send() 콜백으로 합니다. resolve되면 done, reject되면 다음 주기에 재시도합니다. 세그먼트를 pending과 done 중 어디로 보낼지는 그 세그먼트를 닫는 탭의 upload 설정을 따릅니다(#068).
  • 세그먼트 상태: active → pending → done → 삭제. 크기(초안 2MB, #066)나 시간(초안 5분, 옵션 rotate.maxAgeMs)이 차면 로테이션합니다(#021, #036). 파일명의 두 시각은 레코드 ts의 최솟값과 최댓값입니다(#067). 탭이 닫힐 때는 pending으로 옮기지 않고 주인 없는 파일 복구에 맡깁니다(#020).
  • Worker는 별도 파일로 배포하고 workerUrl 옵션을 둡니다. 인라인 빌드는 하지 않습니다.
  • 세그먼트는 JSON 헤더 한 줄 + 순수 JSON Lines입니다. 바이너리 프레임과 CRC32는 쓰지 않습니다(#016). 외부로는 tab, seq, 전역 context를 채운 JSONL을 내보냅니다.
  • 레코드 필드는 ts(Date.now()), lv, msg, ctx, err입니다. tab, seq, 전역 context는 헤더 줄에 둡니다. tabId와 seq는 메인 스레드가 정하고, 레코드 줄은 모두 메인의 flush에서 나옵니다(#061).
  • 쓰기 경로(protocol.html): log() 때 JSON.stringify(#014) → 문자열 큐(#015) → 주기·크기·error 조건으로 flush(#017) → Worker가 쓰고 ack(#018). hidden과 pagehide 때도 flush(#020).
  • 과부하: 메인 버퍼 + 응답 안 온 양이 80%면 debug·info 거절, 100%면 전부 거절. 버린 건수는 flush 때 한 줄로 남깁니다(#019). 쓰기가 실패한 flush도 같은 줄로 남기고, 파일은 쓰기 전으로 되돌린 뒤 로테이션합니다(#064).
  • 같은 탭 subscribe()는 v0.1에 포함하고, flush 때 묶음을 넘깁니다(#023).
  • 숫자(flush 주기 200ms, 256K자, 4M자, 80%, 세그먼트 5분)는 초안이며 벤치마크로 정합니다. flush 주기는 "저사양 모바일에서 flush 비용 ≤ 메인 스레드 1%인 가장 짧은 간격"으로 고릅니다.
  • 공개 API(api.html): 모듈 싱글톤 init() + logger.info(msg, ctx?), setContext, flush, close, subscribe(디버깅용), exportLogs. query는 v0.1에 없습니다(#057). 실패한 logger는 메인 스레드에 부하를 주지 않습니다(#041). 브라우저 페이지가 아니면(SSR 등) 아무것도 하지 않습니다(#062). 최소 레벨 옵션과 persist() 옵션은 없습니다(#069, #065).
  • 세그먼트를 닫고 새로 여는 것은 "로테이션", 새로 열지 않고 옮기기만 하는 것은 "pending으로 옮김"이라고 부릅니다(#037).
  • 압축은 보류합니다.

6단계 결과

범위는 #058, 결과는 benchmark.html에 있습니다.

  • Vitest browser mode(Chromium, Firefox, WebKit) 구성. WebKit은 영구 컨텍스트가 필요합니다.
  • move(), 잠긴 파일 getFile(): 세 엔진 모두 됩니다.
  • bfcache: Chromium에서 sync handle을 쥔 채 들어가고 돌아온 뒤 쓰기도 이어집니다. Firefox와 Safari는 실기기 목록으로 넘겼습니다.
  • Vite 8: 설정 없이 dev와 build 모두 됩니다. Worker는 한 식으로만 만듭니다(#059).
  • 속도: #014, #015, #016 유지. flush 한 번은 최대 약 1,400줄(#042 메모 추가). msgpackr 비교는 뺐습니다(#060).
  • 남은 측정은 구현 단계와 실기기 목록으로 넘겼습니다.

7단계 결과

1~6단계 문서와 결정 #001 ~ #060을 다시 읽고, 구현 전에 비어 있던 것을 정했습니다. 결정은 #061 ~ #069입니다.

  • tabId와 seq는 메인 스레드가 정하고, 레코드 줄은 모두 메인의 flush에서 나옵니다. retention이 지운 pending은 건수만 메인에 보내 drop 줄로 씁니다(#061).
  • 브라우저 페이지가 아니면(SSR, Node 등) import 때 한 번 검사해 처음부터 닫힘 상태로 둡니다. 경고는 없습니다(#062).
  • 실행 중이 아닐 때 exportLogs()는 바로 빈 결과로 resolve합니다(#063).
  • 쓰기 실패는 원인과 상관없이 되돌리기, ok: false ack, drop으로 세기, 로테이션으로 처리합니다. 오류 코드 write-failed를 추가했습니다(#064).
  • persist() 옵션은 두지 않습니다(#065).
  • 세그먼트 크기 상한을 8MB에서 2MB로 낮췄습니다. 실측이 필요합니다(#066).
  • 다른 탭의 활성 세그먼트는 계속 export에서 뺍니다(#054 메모).
  • 파일명의 두 시각은 레코드 ts의 최솟값과 최댓값입니다(#067).
  • 탭마다 upload 설정이 다르면, 세그먼트를 닫는 탭의 설정을 따릅니다(#068).
  • 최소 레벨 옵션은 없습니다. 기록 여부는 호출하는 쪽이 정합니다(#069).
  • 앞 문서에 남아 있던 옛 가정(쿼리 API, 100MB, 백오프, app 필드, Lock 이름의 namespace 등)을 고쳤고, 각 문서의 "검증할 것" 표에 상태를 적었습니다.

8단계(구현)에서 정할 것

설계 결정이 아니라 구현하면서 정하면 되는 값과 순서입니다.

  • 세그먼트 헤더 줄의 키 이름(storage-format.html) → #071
  • tabId 형식(길이, 문자) → #072
  • namespace에 허용할 문자. 디렉터리 이름과 Lock 이름에 안전해야 합니다(#034) → #073
  • ack가 끊겼다고 판단할 시간(worker-unresponsive, #040)
  • retention drop 줄의 ctx 필드(#050, #061)와 쓰기 실패 drop 줄의 필드(#064) → #070
  • 헤더 줄만 있는 주인 없는 파일 처리(지울지, 빈 pending으로 옮길지)
  • Worker는 활성 파일을 만들기 전에 탭 Lock부터 잡습니다. 순서가 바뀌면 다른 탭이 그 파일을 주인 없는 파일로 보고 복구할 수 있습니다(#012)
  • 구현 단계 측정은 benchmark.html에 있습니다.

진행 방식

  • 질문은 한 번에 하나씩 합니다.
  • Lock 설계는 조건 없이 단순하게 둡니다. 모든 탭이 같은 규칙을 따르고, 탭 상태에 따라 달라지는 규칙을 만들지 않습니다(#022).
  • 구성 요소나 기능을 추가하기 전에 "정말 필요한가"를 먼저 따집니다.
  • 결정은 docs/decisions.md에 짧게, 설계 설명은 이 디렉터리의 HTML에 씁니다. 같은 내용을 두 곳에 쓰지 않습니다.
