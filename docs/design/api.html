1. log 호출 인자: 메시지 먼저, context는 선택 (#024)

logger.info('upload done', { fileId: 'a1', ms: 320 })
logger.warn('slow response')

레벨별 메서드는 (msg, ctx?)를 받습니다. 저장 레코드의 msg, ctx(#011)와 그대로 대응합니다.

안모양사례판단
Ainfo('msg', ctx?)winston, 대부분의 JS 로거채택 스키마와 1:1, 가장 흔하고 읽기 쉬움
Binfo(ctx, 'msg')pino, bunyan탈락 객체를 앞에 두는 이유는 printf 포맷 지원인데, opfslogd는 포맷을 하지 않음
Cinfo('a', obj, 123)loglevel, consola탈락 메시지와 context 경계가 모호. 인자 전체를 저장해야 하고 쿼리가 msg, ctx에 기댈 수 없음

2. Error 전달: ctx.err 또는 ctx 자체 (#025)

JSON.stringify(new Error())는 {}입니다. 그래서 Error는 찾아서 레코드의 err 필드(name, message, stack, #011)로 옮깁니다.

try { ... } catch (e) {
  logger.error('upload failed', { err: e, fileId })   // 정식 방법
  logger.error('upload failed', e)                    // 이것도 처리
}
  • ctx.err가 Error이면 err 필드로 옮기고 ctx에서는 뺍니다. 사용자 객체는 바꾸지 않습니다.
  • ctx 자체가 Error이면 err 필드로 옮기고, 레코드에 ctx는 없습니다.
  • ctx.err가 Error가 아니면(throw 'text' 등) ctx에 일반 값으로 남습니다.
  • 모든 레벨에서 동작합니다.
  • ctx 안 깊은 곳의 Error({ last: { error: e } })는 변환하지 않고 {}로 저장됩니다. 문서에서 Error는 err 키나 ctx 자리에 넘기라고 안내합니다.

깊은 Error를 처리하지 않는 이유: 모든 깊이를 처리하려면 JSON.stringify replacer가 필요합니다. replacer가 있으면 V8 빠른 경로를 못 쓰고 키마다 JS 함수를 호출하므로, 드문 경우를 위해 모든 log()가 느려집니다(#014의 비용 추정은 replacer가 없다는 전제). 최상위 값만 훑는 방법은 매번 비용을 내면서도 절반만 해결해 규칙이 애매해집니다.

정식 방법을 { err: e }로 둔 이유: TS strict에서 catch 변수는 unknown이라 Record<string, unknown>에 캐스팅 없이 들어갑니다. ctx 자체가 Error인 경우를 처리하는 이유: JS에서 흔한 호출이고, 처리하지 않으면 내용이 {}로 조용히 사라집니다. 세 번째 인자(error(msg, err, ctx?))는 #024 모양을 깨서 탈락했습니다.

err.cause 체인 저장 (#026)

"err": {"name":"Error","message":"upload failed","stack":"...",
        "cause": {"name":"TypeError","message":"Failed to fetch","stack":"..."}}
  • cause도 같은 모양으로 재귀 저장합니다. 깊이는 최대 5단계입니다.
  • 체인 안에서 이미 나온 Error를 다시 가리키면(순환) 거기서 멈춥니다.
  • Error가 아닌 cause는 일반 값으로 저장하고, 직렬화가 안 되면 #011처럼 대체값을 넣습니다.

이유: new Error(msg, { cause })로 감싸는 경우가 흔하고, 진짜 원인은 대개 안쪽 Error에 있습니다. Chrome의 stack에는 cause가 들어가지 않습니다. 비용은 Error가 있는 레코드에만 듭니다. 선례: pino 기본 err serializer(재귀), Sentry LinkedErrors(기본 깊이 5), Node util.inspect.

Error의 추가 속성 (#027)

"err": {"name":"HttpError","message":"bad","stack":"...","status":503,"code":"UPSTREAM_DOWN"}

Error 자신의 열거 가능한 속성(Object.keys)을 err 안에 복사합니다. cause의 각 단계에도 똑같이 적용합니다. name, message, stack, cause와 이름이 겹치면 고정 필드가 이깁니다. 값 처리는 ctx와 같습니다.

이유: 앱의 Error 클래스는 status, code 같은 핵심 정보를 속성으로 갖는 경우가 많습니다. 비용은 Error가 있는 레코드에만 듭니다. 선례: pino 기본 err serializer, Node util.inspect.

커버하지 않는 것: DOMException.code는 프로토타입의 getter라 복사되지 않습니다. 대신 name(예: QuotaExceededError)에 같은 정보가 있습니다. AggregateError.errors는 열거 불가 속성이라 지금은 저장하지 않습니다.

3. logger를 얻는 방법: 모듈 싱글톤 + init() (#028)

// main.ts (진입점에서 한 번)
import { init } from 'opfslogd'
init({ upload: { send } })

// 어디서든
import { logger } from 'opfslogd'
logger.info('clicked', { id })

기준은 "사용자가 아무 생각 없이 쓸 수 있는가"입니다. 호출하는 쪽은 패키지에서 바로 import하면 되고, 앱이 logger 모듈을 따로 만들 필요도, 실수로 여러 개 만들 일도 없습니다. 이름(logger, init)은 초안입니다.

init() 전 기록

init() 전에 들어온 기록도 평소처럼 직렬화해 큐에 넣습니다(#014, #015). Worker가 생길 때까지 flush만 미룹니다. 버퍼 상한과 거절 규칙(#019)은 그대로라, init()을 끝내 부르지 않으면 큐가 상한까지 찬 뒤 거절됩니다. 큐는 Worker 없이도 존재하므로 추가되는 규칙은 "Worker가 없으면 flush하지 않는다" 하나뿐입니다.

선례

분류라이브러리방식

범용 로거loglevel, consola, winston, electron-log기본 인스턴스 + 팩토리

팩토리(createLogger())는 앱이 logger 모듈을 직접 두어야 해서 탈락했습니다. 여러 인스턴스가 필요해지면 나중에 API를 깨지 않고 추가할 수 있습니다. 대가로 테스트가 전역 상태를 공유하므로 초기화 수단(close())이 필요합니다.

두 번째 init(): 무시하고 경고 한 번 (#029)

처음 init() 뒤의 호출은 아무것도 하지 않고, 처음 옵션이 유지됩니다. "이미 init됨, 바뀐 옵션은 새로고침 후 적용"이라는 console.warn을 한 번 출력합니다.

  • 두 번 불리는 경우는 흔합니다: HMR이 진입 모듈을 다시 실행, React StrictMode, 컴포넌트 안의 init().
  • 예외를 던지면 HMR 때마다 화면이 깨집니다.
  • 새 옵션으로 다시 시작하려면 Worker를 재시작해야 합니다. tabId와 탭 Lock이 바뀌고, 활성 세그먼트는 고아가 되고, 큐를 옮겨야 합니다. HMR 한 번에 낼 비용이 아닙니다.
  • 선례: Datadog은 경고 후 무시. Sentry는 client를 교체하는데, 파일이나 Lock을 갖지 않으니 가능한 방식입니다.

close(): 기록 중지 (#030)

close(): Promise<void>는 순서대로 큐 flush와 ack 대기(#018), 활성 세그먼트를 pending으로 옮기기(새 세그먼트는 열지 않음), Lock 해제와 Worker 종료를 합니다.

그 뒤의 log()는 버립니다. 큐에 넣지 않고, 의도한 중지이므로 버린 건수 줄(#019)도 남기지 않습니다. log()는 여전히 예외를 던지지 않습니다(#011). close()마다 처음 버리는 호출에서 기록이 중지됐다는 console.warn을 한 번 출력합니다.

경고는 #029와 마찬가지로 환경 구분 없이 항상 출력합니다. 개발 환경만 가려내려면 process.env.NODE_ENV가 필요한데, AGENTS.md가 src/에서 금지하는 Node 전역입니다. 치환해 주는 번들러도 일부뿐이고, 흔한 가드 typeof process !== 'undefined' && …는 Vite와 webpack 5 번들에서 경고를 아예 꺼 버립니다(process.env.NODE_ENV만 치환하고 process는 없음). 프로덕션 비용은 잘못 썼을 때 콘솔 한 줄입니다. 나중에 개발 전용으로 바꿔도 API는 바뀌지 않으므로, 요청이 오면 그때 바꿉니다. close() 뒤의 init()은 정상 시작입니다(#029의 두 번째 호출이 아님).

init 전 (큐에 쌓음) → 실행 중 → 닫힘 (버림) → init() → 실행 중
  • 용도: 테스트의 전역 상태 초기화(#028), 로그아웃이나 수집 동의 철회 때 기록 중지.
  • init 전 상태로 돌아가면, 동의 철회 뒤에도 앱과 서드파티 패키지의 기록이 큐에 쌓이고 다음 init() 때 파일에 써집니다. 사용자가 거부한 기간의 로그가 남는 셈입니다.
  • 해제된 리소스에 접근하는 것과 비슷하므로 개발자가 알아야 합니다. 다만 logger는 공유 객체라 다른 코드(서드파티 포함)는 닫혔는지 알 수 없으므로 예외를 던질 일은 아닙니다.
  • 여기서 pending으로 옮기는 것은 #020과 충돌하지 않습니다. #020은 페이지가 사라지는 중이라 비동기 작업이 끝난다는 보장이 없어서 옮기지 않습니다. close()는 Worker가 살아 있을 때 await합니다.

4. 전역 context (#031)

그 탭의 모든 로그에 공통으로 붙는 값입니다. 파일에는 세그먼트 헤더 줄에 한 번 저장하고(#011), export와 upload 때 모든 줄에 다시 붙입니다.

실행 중 변경: 바뀌면 새 세그먼트

context는 init()에서 처음 정하고, 실행 중에 바꿀 수 있습니다. 설정할 때 직렬화합니다(#014). 바뀌면:

  1. 메인 스레드가 큐를 flush한 뒤 새 context를 Worker에 보냅니다.
  2. Worker가 로테이션합니다: 활성 세그먼트를 pending으로 옮기고, 새 context를 헤더에 담은 새 세그먼트를 엽니다. 활성 세그먼트에 레코드가 아직 없으면 헤더 줄만 다시 씁니다.

메시지 순서가 유지되므로 변경 전 기록은 옛 context, 변경 후 기록은 새 context를 갖습니다. seq는 세그먼트를 넘어 이어집니다(#016). 로테이션은 이미 있는 동작(#021)이라 새 메커니즘이 필요 없고, 변경은 로그인·로그아웃처럼 드물어 세그먼트가 늘어나는 비용은 작습니다. 요청마다 바뀌는 값은 레코드 ctx에 넣으라고 안내합니다.

탈락: init 때만 지정(로그인 후 사용자 ID 불가), 파일 안 특수 줄(#016의 "줄은 ts, lv로 시작"과 "seq = 줄 번호"가 깨짐), 매 레코드 복사(#011이 아끼던 바이트 낭비).

변경 API: setContext(partial) 얕은 병합 (#032)

init({ context: { version: '2.3.1', env: 'prod' } })
setContext({ userId: 'u42' })        // 로그인 → { version, env, userId }
setContext({ userId: undefined })    // 로그아웃 → { version, env }
  • 최상위 키만 병합합니다. 중첩 객체는 통째로 교체합니다.
  • 값이 undefined인 키는 삭제합니다.
  • 병합 결과의 직렬화 문자열이 이전과 같으면 아무것도 하지 않습니다(새 세그먼트 없음).
  • init({ context })는 init 시점의 setContext(context)와 같습니다. init 전 setContext() 값은 유지되고, 겹치는 키는 init 쪽이 이깁니다.
  • close()는 context를 비웁니다. 다음 init()은 깨끗하게 시작합니다(#030).

전체 교체(A)는 로그인 때 setContext({ userId })만 넘기면 version, env가 조용히 사라지는 함정이 있어 탈락했습니다. 키 단위 함수 쌍(B, Datadog)보다 함수가 하나 적고, 키 여러 개를 한 번에 바꿔도 세그먼트 전환은 한 번입니다.

내보낸 JSONL의 모양: context 아래 중첩 (#033)

{"ts":1793251200123,"lv":"info","msg":"clicked","ctx":{"id":7},"tab":"k3f9","seq":0,"context":{"userId":"u42","version":"2.3.1"}}

최상위에 합치면(Datadog 방식) 사용자 키가 msg, seq 같은 예약 필드와 충돌합니다. ctx를 따로 둔 이유(#011)와 같습니다. 이름은 API(init({ context }), setContext)와 맞췄습니다. 한 줄에 ctx와 context가 함께 있어 헷갈릴 수 있으며, 대안 이름은 global입니다. 이름은 잠정이고 1.0 전에 다시 볼 수 있습니다.

5. 기본 옵션

namespace: 같은 출처의 앱 분리 (#034)

init({ namespace })(기본값 'default')는 OPFS 디렉터리 opfslogd/{namespace}/를 고르고, 모든 Lock 이름 앞에 붙습니다: opfslogd:{ns}:upload, opfslogd:{ns}:retention, opfslogd:{ns}:tab:{tabId}. #012, #022의 Lock 이름을 고친 것이며, 세그먼트 파일명(#012, #013)은 그대로입니다.

OPFS와 Web Locks는 출처 단위입니다. 같은 출처의 앱 두 개(user.github.io/app1과 /app2, 회사 도메인 하나의 여러 앱, 마이크로 프론트엔드)가 네임스페이스 없이 쓰면 디렉터리와 업로드 Lock을 공유합니다. 앱 1의 send()가 앱 2의 로그를 앱 1의 백엔드로 보내고, 보존 용량도 같이 씁니다. 조용히 일어나고 데이터 유출에 가깝습니다. 나중에 깨지지 않게 추가하려 해도 지금 opfslogd/default/ 구조가 필요하므로, 옵션 자체의 비용은 문자열 하나입니다.

알리는 방법: 옵션의 JSDoc(IDE에서 마우스를 올리면 보임)과 README의 "같은 도메인에 앱이 여러 개라면" 절에 사고 시나리오를 그대로 씁니다. 런타임 감지와 경고는 하지 않습니다. 두 앱을 구별할 단서가 없습니다(location.pathname은 SPA 라우트마다, Worker 스크립트 URL은 해시 배포마다 바뀜). 오탐 경고는 경고를 무시하는 습관만 만듭니다. "upload 설정 + 기본 namespace"에 경고하면 앱이 하나인 거의 모든 사용자가 경고를 봅니다.

공개 옵션으로 여는 내부 기본값: 세그먼트 시간 상한만 (#035)

옵션 이름: rotate.maxAgeMs (#036)

init({ rotate: { maxAgeMs: 300_000 } })

"세그먼트"는 내부 용어입니다. 지금 파일을 닫고 새 파일을 시작하는 동작의 표준 용어는 로테이션입니다: logrotate(daily, size), winston-daily-rotate-file(frequency, maxSize), pino-roll(frequency, size). 크기 상한을 나중에 열면 rotate.maxBytes로 들어갑니다. Ms 접미사는 upload.intervalMs(#007)와 맞췄습니다. upload가 없어도 적용되므로(#021) upload 아래에 두지 않습니다.

6. flush(timeoutMs?): Promise<boolean> (#038)

const written = await flush()       // 기본 timeout 5초(초안)
const written = await flush(1000)

지금 큐를 Worker로 보내고, 호출 시점에 큐에 있던 기록이 모두 파일에 쓰이면(ack, #018) true, timeoutMs 안에 안 되면 false로 resolve합니다. reject하지 않습니다.

  • init() 전: 기록이 Worker를 기다립니다. 시간 안에 init()되고 쓰이면 true, 아니면 false.
  • close() 후: 큐가 비어 있으므로(#030) 바로 true.

숨겨질 때, pagehide(#020), close()는 자동으로 flush하고 export도 스스로 flush합니다. 그래도 테스트, 그리고 "디스크에 쓰인 뒤 다음 동작"이 필요한 경우에 쓰입니다. timeout이 없으면 Worker가 죽거나 멈췄을 때 await flush()가 영원히 끝나지 않습니다. reject 대신 false라 try/catch가 필요 없습니다. 선례: Sentry flush(timeout), pino logger.flush(cb).

7. 앱에 알리는 콜백

버린 건수: 별도 콜백 없음 (#039)

버린 건수는 flush 때 로그 한 줄로 남고(#019), subscribe()가 그 줄을 묶음과 함께 받습니다(#023). 별도 onDrop은 같은 정보의 세 번째 경로일 뿐이고, 앱이 반응할 일도 드뭅니다. 나중에 추가해도 API가 깨지지 않습니다. drop 줄을 알아보는 방법은 #044를 보세요.

내부 오류: init({ onError }) (#040)

init({
  onError(err) {        // err: OpfslogdError (Error 상속)
    err.code            // 'opfs-unavailable' | 'worker-load-failed' | ...
    err.cause           // 원래 오류(DOMException 등)
    Sentry.captureException(err)
  },
})
코드(초안)상황
opfs-unavailableOPFS를 못 씀(구형 브라우저, 일부 사생활 보호 모드)
worker-load-failedWorker 파일 로드 실패(workerUrl 오류, CSP 차단)
quota-exceeded저장 공간 부족
worker-unresponsiveack가 끊김. Worker가 죽었거나 멈춤(#018)
unreadable-file새 포맷 파일이라 건너뜀(#013)
  • send() 실패는 넣지 않습니다. 앱이 만든 함수이고 라이브러리가 재시도합니다(#007).
  • onError가 없으면 코드마다 console.error를 한 번 출력합니다(#029, #030과 같은 규칙). 있으면 출력하지 않습니다.
  • onError가 던진 예외는 잡아서 무시합니다(#023의 subscriber 격리와 같음).
  • 코드는 마이너 버전에서 늘어날 수 있으므로, 모르는 코드도 처리하게 안내합니다.

1단계에서 "오류는 콜백으로만" 알리기로 했습니다(앱 코드로 예외를 던지지 않음). 대부분 Sentry 같은 수집기로 넘기므로 Error 인스턴스가 맞고, code로 분기하며 cause로 원래 오류를 보존합니다.

저장을 시작할 수 없을 때: 닫힘 상태와 같게 (#041)

원칙: 실패한 logger는 메인 스레드에 부하를 주거나 앱 동작에 영향을 주면 안 됩니다.

opfs-unavailable이나 worker-load-failed(#040)가 나면 #030의 닫힘 상태로 바뀝니다. log()는 상태만 확인하고 바로 반환합니다(직렬화, 타이머, 큐 없음). init 전에 쌓인 큐는 버리고, subscriber도 아무것도 받지 않습니다. 원인은 이미 onError나 console.error로 알렸으므로 #030의 "기록 중지" 경고는 출력하지 않습니다. flush()는 close() 후처럼 바로 true입니다(#038).

이 두 코드에만 적용합니다. quota-exceeded는 retention이 공간을 비우면, worker-unresponsive는 ack가 다시 오면 회복될 수 있습니다. ack가 끊긴 동안에는 #019가 직렬화 전에 거절하므로 비용이 작습니다.

flush는 계속하면서 subscriber에게만 넘기는 안은, 저장할 곳이 없는데 직렬화와 flush 비용을 계속 내므로 탈락했습니다. OPFS가 없는 브라우저는 드물어 디버그 패널을 포기하는 비용이 작습니다.

8. subscribe()

넘기는 형태: 파싱된 객체, export 줄과 같은 모양 (#042)

subscribe((records) => {
  for (const r of records) panel.add(r.lv, r.msg, r.ctx)
})

flush마다 묶음을 한 번 JSON.parse해서 LogRecord[]로 넘깁니다. 모양은 export 줄과 같습니다(ts, lv, msg, ctx, err, tab, seq, context, #033). 여러 subscriber가 같은 배열을 공유하므로 읽기 전용으로 다루라고 안내합니다. 레코드마다 드는 Object.freeze 비용은 내지 않습니다.

디버그 패널, 콘솔 출력, 테스트 모두 객체가 필요하므로 문자열로 넘기면 모든 사용자가 같은 파싱 코드를 씁니다. 파싱 비용은 구독한 앱만 내고, 구독이 없으면 0입니다(#023). 앱이 고른 비용이라 #041의 원칙과 충돌하지 않습니다.

해제: 반환된 함수 호출, 용도는 디버깅으로 명시 (#043)

const off = subscribe((records) => { ... })
off()

// React
useEffect(() => subscribe(fn), [])
  • 해제 함수를 여러 번 불러도 안전합니다.
  • init() 전에도 구독할 수 있고, init 후 첫 flush부터 받습니다.
  • close()는 구독을 모두 해제합니다(#032에서 context를 비우는 것과 같음).
  • JSDoc과 README에 용도를 명시합니다: 디버깅과 개발용(앱 안 디버그 패널, 개발 중 콘솔 출력, 테스트). 서버로 로그를 보내는 것은 upload의 일입니다.

주 용도인 디버그 패널은 React useEffect 정리 함수와 바로 맞물립니다. unsubscribe(fn)은 인라인 화살표 함수를 해제할 수 없고, AbortSignal은 단순한 경우에도 AbortController가 필요합니다. 용도를 명시하는 이유: subscribe()는 운영용 전송 경로로 맞지 않습니다. 파일에 쓰기 전에 전달되어 크래시 때 잃고, flush마다 파싱 비용(#042)이 들며, 재시도나 배압 제어가 없습니다.

drop 줄 구분: 고정 문자열을 약속으로 문서화 (#044)

drop 줄(#019)의 msg는 항상 "opfslogd: records dropped"이고 ctx.reason이 있습니다. 둘을 바뀌지 않는 약속으로 문서화하고, subscriber와 서버는 이 값과 비교해 알아봅니다. 서버는 JS가 아닐 수도 있어 어차피 msg 문자열이 어디서나 약속이 됩니다. 판별 함수(isDropRecord())는 한 줄 비교치고 공개 API가 늘어나고, 표시 필드는 라이브러리가 만드는 줄이 하나뿐인데 저장 스키마(#011)를 바꿉니다.

9. upload 옵션

끝나지 않는 send(): meta.signal과 upload.timeoutMs (#045)

upload: {
  async send(file, meta) {
    await fetch(url, { method: 'PUT', body: file, signal: meta.signal })
  },
  timeoutMs: 60_000,   // 초안
}

send()가 upload.timeoutMs 안에 끝나지 않으면 signal을 abort하고, 실패로 처리해 실행을 끝내고 업로드 Lock을 놓습니다(#022). 세그먼트는 pending/에 남고, 뒤늦게 끝난 결과는 무시합니다. 끝나지 않는 send()는 Lock을 쥐고 모든 탭의 업로드를 멈추게 합니다. signal을 fetch에 넘기면 실제 요청까지 취소됩니다. 뒤늦은 성공으로 생기는 중복은 #007의 at-least-once와 segmentId로 처리됩니다. 필요한 시간은 네트워크와 백엔드마다 달라 공개 옵션으로 두고, 기본값은 측정해서 정합니다(8MB를 약 1Mbps로 올리면 1분 가까이 걸림).

실패 후 재시도: 고정 주기, 첫 실패에서 실행 중단 (#046)

백오프는 없습니다. send()가 reject되거나 시간 초과(#045)되면 그 실행을 바로 끝내고, 남은 세그먼트는 다음 upload.intervalMs 실행을 기다립니다. 실패한 세그먼트도 pending/에 남아 그때 다시 시도합니다.

클라이언트마다 주기당 한 번 시도하고 첫 실패에서 멈추므로, 장애 중에도 요청 빈도가 평소보다 늘지 않습니다. 업로드하는 탭은 실행마다 바뀌므로(#022) 백오프에는 탭 간 공유 상태가 필요한데, 얻는 것에 비해 큽니다. 나중에 옵션으로 추가해도 깨지지 않습니다. 남는 위험은 장애가 끝나는 순간 모든 클라이언트가 쌓인 세그먼트를 한꺼번에 올리는 것입니다.

한 실행에 올리는 개수: 제한 없음, 부하 테스트 후 재검토 (#047)

한 실행은 pending/ 세그먼트를 오래된 것부터 하나씩 올리고, 다 올리거나 실패하면(#046) 끝납니다. 클라이언트 하나의 동시 요청은 1개입니다. 장애 복구 직후의 몰림은 "모든 클라이언트가 동시에 시작"에서 오며, 이는 평소 주기마다 있는 패턴입니다. 제한값의 근거가 아직 없고, 백엔드가 429 같은 오류를 주면 send()가 reject해 실행이 멈추므로 서버가 속도를 조절할 수단이 있습니다.

send(file, meta) 인자 (#048)

send(file: Blob, meta: {
  segmentId: string   // pending 파일명에서 확장자를 뺀 것: "{startTs}_{endTs}_{tabId}"
  sha256: string      // file의 hex 해시
  size: number        // file 바이트 수
  from: number        // 첫 레코드 ts
  to: number          // 마지막 레코드 ts
  signal: AbortSignal // #045
}): Promise<unknown>  // resolve 값은 무시
  • file은 export 모양 JSONL(#007, #033)의 Blob입니다(application/x-ndjson). fetch body에 그대로 넣을 수 있고, 압축은 사용자가 CompressionStream으로 할 수 있습니다(#016 압축 보류와 맞음). 문자열이면 최대 8MB를 복사합니다.
  • segmentId는 파일명을 재사용합니다. tabId가 들어 있어 겹치지 않고, pending으로 옮긴 뒤에는 바뀌지 않습니다.
  • 레코드 수(서버가 줄 수를 세면 됨)와 namespace(send는 앱마다 정의)는 넣지 않습니다. 필드는 나중에 추가해도 깨지지 않습니다.

첫 업로드 시점: init 후 페이지가 한가해지면 (#049)

upload.intervalMs 기본값은 1분(초안, #021)입니다. 첫 실행은 한 주기를 기다리지 않습니다. init() 후 load 이벤트와 requestIdleCallback(없으면, 예를 들어 Safari에서는 짧은 setTimeout)을 기다려 한 번 실행하고, 그다음부터 주기마다 실행합니다. 실행은 여전히 ifAvailable(#022)이라 여러 탭이 동시에 열려도 한 탭만 실행합니다.

주기 타이머만 있으면 짧은 세션(30초 쓰고 닫는 모바일 사용자)에서는 업로드가 한 번도 돌지 않고 지난 세션의 밀린 세그먼트도 계속 기다립니다. init 직후 바로 실행하면 세그먼트 변환, sha256, 네트워크 요청이 페이지 로드와 겹칩니다.

10. retention 옵션

상한의 종류: 크기와 기간 (#050)

retention.maxBytes와 retention.maxAgeMs. 보존 정리 실행(#022)은:

  1. 끝 시각(파일명, #012)이 maxAgeMs보다 오래된 닫힌 세그먼트를 done이든 pending이든 지웁니다.
  2. 그래도 합계가 maxBytes를 넘으면 #007대로 done부터, 그다음 오래된 pending을 지웁니다.

지운 pending은 ctx.reason이 "retention"인 drop 줄(#019)로 남깁니다. 다른 필드는 구현 때 정합니다(파일을 읽지 않으면 레코드 수를 모름).

로그에는 사용자 ID 같은 값(#031)이 들어갑니다. 로그가 적은 앱은 크기 상한에 닿지 않아 기간 상한이 없으면 기기에 영원히 남습니다. 필요한 만큼만 보관하는 것이 개인정보 보호의 기본 원칙(GDPR 저장 제한)입니다. 끝 시각이 파일명에 있어 파일을 열지 않고 판단합니다.

기간 기본값: 7일 (#051)

  • Tencent Mars xlog(WeChat의 모바일 로그 라이브러리)의 기본 보존 기간은 10일입니다(2차 자료 기준, 공식 소스는 미확인). Meituan Logan의 기본값은 확인하지 못했습니다.
  • 버그 리포트는 대개 문제 후 며칠 안에 들어옵니다.
  • Safari의 ITP는 사용자가 Safari를 쓴 날 기준 7일 동안 상호작용하지 않은 사이트의 스크립트 저장소를 모두 지웁니다. WebKit 관리자는 Bugzilla 276998에서 OPFS도 포함된다고 답했지만 공식 문서는 없습니다. 7일이면 어느 쪽이든 그 안에 듭니다. 자주 방문하는 사용자는 카운터가 초기화되므로 더 긴 설정도 유지됩니다.

근거가 약합니다. 7일이 10일이나 14일보다 낫다는 강한 근거는 없으며, 실사용 데이터로 다시 봅니다.

크기 기본값: 50MB 초안, 공개 옵션 (#052)

namespace 안 세그먼트 파일의 디스크 바이트 합계로 셉니다. init({ retention: { maxBytes } })로 바꿀 수 있습니다. 지우는 대상은 닫힌 세그먼트뿐이고(#050), 활성 세그먼트는 합계에 들어가지만 지우지 않습니다.

다른 라이브러리에서 쓸 만한 근거를 찾지 못했고, 브라우저 할당량(디스크의 수십 %)은 기준이 되지 않습니다. 50MB는 초안이며 실사용 데이터로 다시 봅니다. 알맞은 값은 앱의 로그량과 upload 사용 여부에 따라 달라 공개 옵션으로 둡니다.

실행 시점: 첫 idle 때 upload보다 먼저, 이후 1분마다(내부값) (#053)

첫 retention 실행은 첫 upload 실행(#049)과 같은 시점에, 그보다 먼저 돕니다. 이후 주기는 내부값 1분(upload 기본 주기와 같음)이고 공개하지 않습니다. upload가 없는 앱도 같습니다. retention 실행은 주인 없는 active/ 파일도 복구하므로(#012), 먼저 돌면 지난 세션의 크래시나 닫힌 탭의 파일이 pending으로 옮겨져 같은 첫 실행에서 업로드됩니다. 비용은 디렉터리 목록, 파일명 비교, locks.query() 한 번으로 작습니다.

11. export

포함 범위: 닫힌 세그먼트 + 내 탭의 활성 세그먼트 (#054)

대상포함
닫힌 세그먼트(pending, done)포함
내 탭의 활성 세그먼트포함 내 Worker가 flush 후 자기 handle로 읽음
다른 탭의 활성 세그먼트제외 결과에 제외 개수를 표시

주 용도는 문제가 난 탭에서 보내는 버그 신고이고, 가장 중요한 것은 그 탭의 최근 몇 분입니다. 다른 탭의 로그도 마지막 로테이션 시점(기본 최대 5분 전)까지는 닫힌 세그먼트로 들어갑니다. 다른 탭에 활성 내용을 요청하면(BroadcastChannel) #006에서 피한 탭 간 경로와 응답 없는 탭 처리가 생깁니다. #021의 "닫힌 파일만 export 대상"을 고칩니다.

API 모양: exportLogs({ from?, to? }) → { file, skipped } (#055)

const { file, skipped } = await exportLogs({ from?: number, to?: number })
// file: Blob (application/x-ndjson), export 줄 모양(#033)
// skipped: { activeOtherTabs: number, unreadable: number }
  • export는 예약어라 exportLogs입니다.
  • Blob은 다운로드 링크(URL.createObjectURL)나 fetch body로 바로 쓰이고, send()의 file(#048)과 같은 형식입니다.
  • from, to로 시간 범위를 정합니다. 파일은 파일명 시각(#012), 줄은 앞부분 ts(#016)로 걸러 JSON 파싱이 필요 없습니다. 버그 신고에 50MB 전체는 과합니다.
  • skipped는 제외한 다른 탭 활성 세그먼트 수(#054)와 새 포맷이라 읽지 못한 파일 수(#013)입니다. 오류가 아니라 정보라 onError가 아닌 결과에 담습니다.
  • 레벨이나 문자열 조건은 query(12단위)의 일입니다.

줄 순서: 탭을 넘어 시간순 병합 (#056)

스트리밍 k-way merge로 합칩니다. 열린 파일마다 읽는 위치를 하나씩 두고, 가장 이른 ts의 줄을 다음으로 내보냅니다. 파일은 시작 시각 순(#012)으로, 출력 시점과 시간 범위가 겹칠 때만 열므로 동시에 열린 파일 수는 동시에 열려 있던 탭 수 정도입니다. ts는 줄 앞부분 문자열로 비교해 파싱하지 않습니다(#016). 한 탭 안에서는 시계가 뒤로 간 경우에도 항상 seq 순서를 지킵니다(#011).

export의 주 독자는 버그 신고를 읽는 사람입니다. 파일명 순으로 이어 붙이면 겹친 탭의 줄이 구간마다 섞여 읽기 어렵습니다. 전체를 메모리에서 정렬하면 최대 50MB를 파싱해야 합니다.

12. query

v0.1에는 넣지 않음 (#057)

버그 신고 파일은 exportLogs({ from, to })(#055), 실시간 디버그 패널은 subscribe()(#042), 서버 검색은 upload가 맡습니다. 앱 안에서 과거 로그를 보려면 짧은 범위의 exportLogs() 결과를 줄 단위로 파싱하면 됩니다(디버깅 용도라 비용 감당 가능). query는 필터, 개수 제한, 페이지, 객체 결과까지 공개 API가 크게 늘고 한번 열면 바꾸기 어렵습니다(#035). 저장 포맷은 이미 지원하므로(#016의 고정 위치 ts, lv) 실제 요구를 보고 나중에 추가해도 깨지지 않습니다. 세그먼트 스캔 벤치마크(#016)는 export 시간 필터가 같은 스캔을 쓰므로 유지합니다.
