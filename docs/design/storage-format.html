opfslogd 저장 포맷

상태: 3단계 완료 (남은 항목은 이후 단계로 넘김) · 최종 수정 2026-10-29 · 관련 결정: docs/decisions.md #010, #011, #012, #013 · 상위 문서: architecture.html

세그먼트 파일은 바이너리 프레임의 연속이고, 각 프레임 안에는 UTF-8 JSON Lines가 들어갑니다. 이 포맷은 라이브러리 내부 전용이며, 내보내기(export)와 업로드 때는 순수 JSON Lines로 변환합니다.

1. 전제: 파일 포맷이 곧 전송 포맷

  • 메인 스레드는 flush할 때 레코드를 바이트로 인코딩해 Worker에 ArrayBuffer로 transfer합니다.
  • Worker는 받은 바이트에 다시 인코딩하지 않고 그대로 파일에 덧붙입니다.
  • 그래서 직렬화는 메인 스레드에서 한 번만 일어납니다. 객체를 그대로 postMessage로 보내면 structured clone(직렬화 1회)과 Worker 쪽 재인코딩(1회)으로 두 번이 됩니다.
  • 결국 포맷 선택은 "메인 스레드가 가장 싸게 인코딩할 수 있는 형태가 무엇인가"의 문제입니다.

2. 인코딩 방식

A. 순수 JSON LinesB. 순수 바이너리C. 바이너리 프레임 + JSON Lines
인코딩 속도빠름. 네이티브 JSON.stringify + TextEncoder.encodeInto고정 필드는 빠르지만, 임의 객체는 JS로 구현한 인코더가 필요A와 같음
런타임 의존성없음직접 구현하거나 의존성 추가없음
크기키 이름이 레코드마다 반복됨가장 작음 (약 20~30% 절약)A와 거의 같음
손상 감지잘린 마지막 줄만 감지길이와 CRC로 감지프레임마다 길이와 CRC32로 감지
쿼리 시 건너뛰기모든 줄을 파싱해야 함레코드 단위로 가능프레임 단위로 가능 (시간 범위, 레벨 비트마스크)
판정탈락탈락채택
레코드마다 바이너리 헤더를 붙이는 방식은 넣지 않았습니다. 프레임 단위로 건너뛰는 것만으로 쿼리에 충분하다고 봤습니다. 벤치마크에서 쿼리가 병목으로 나오면 포맷 버전을 올려 추가합니다.

3. 세그먼트 구조

프레임 헤더 필드 (초안)

필드 목록은 확정했고, 바이트 배치와 크기는 미결정입니다.

필드용도
magic프레임 시작 표시. 복구할 때 위치 확인
headerLength프레임 헤더 길이. 새 버전이 헤더 끝에 필드를 추가해도 이전 버전은 이 길이만큼 건너뛰고 읽음
flags16비트. 지금은 0. 압축 같은 호환되지 않는 기능을 비트로 표시. 이전 버전은 모르는 비트가 켜진 프레임을 읽지 않음
payload 길이다음 프레임 위치 계산, 잘린 프레임 감지
CRC32payload 손상 감지. JS 구현으로 수백 MB/s가 나오고, 목표 처리량은 약 2MB/s라 비용은 무시할 수준
레코드 수통계, 버린 건수 계산
ts 최솟값/최댓값시간 범위 쿼리에서 프레임 건너뛰기
seq 범위탭 안 순서, 누락 감지
레벨 비트마스크레벨 쿼리에서 프레임 건너뛰기 (예: error가 없는 프레임은 파싱하지 않음)

브라우저에서 바이너리 다루기

OPFS의 sync handle은 원래 바이트(ArrayBuffer, TypedArray)만 받습니다. 텍스트도 TextEncoder로 바이트로 바꿔서 씁니다. 프레임 헤더는 DataView로 정해진 위치에 정수와 실수를 기록합니다.

const view = new DataView(buf)
view.setUint32(0, MAGIC)
view.setUint32(4, payload.byteLength, true)  // little-endian
view.setUint32(8, crc32(payload), true)
view.setFloat64(16, minTs, true)
new Uint8Array(buf, HEADER_SIZE).set(payload)
handle.write(new Uint8Array(buf), { at: offset })

4. 레코드 스키마

내부 JSONL 한 줄의 형태입니다.

{"ts":1793251200123,"lv":"error","msg":"결제 실패","ctx":{"userId":42},"err":{"name":"TypeError","message":"…","stack":"…"}}
필드필수내용
ts✓Date.now() 밀리초 정수 (wall clock). 시계가 뒤로 갈 수 있으므로 탭 안 순서는 seq로 판단
lv✓"debug" · "info" · "warn" · "error"
msg✓문자열
ctx사용자 부가 정보. 별도 필드에 묶어서 예약 필드와 키가 충돌하지 않게 함
errError를 name, message, stack으로 풀어서 저장. JSON.stringify(new Error())는 {}가 되기 때문

레코드에 넣지 않고 헤더에 한 번만 두는 값

값위치이유
tab (탭 ID)파일 헤더세그먼트 하나는 탭 하나 소유
seq (탭 안 순번)프레임 헤더의 seq 시작값 + 줄 번호계산으로 복원 가능
전역 context (앱 버전, 세션 ID 등)파일 헤더init()에서 한 번 정해지는 값

export와 upload에서 JSONL로 변환할 때 이 값들을 각 줄에 다시 채워 넣습니다. 레코드마다 수십 바이트를 아끼며, 초당 1만 건이면 초당 수백 KB에 해당합니다.

// 내보낸 JSONL 한 줄
{"ts":1793251200123,"tab":"k3f9","seq":1042,"lv":"error","msg":"결제 실패","ctx":{"userId":42},"app":{"version":"2.3.1"}}

내보낸 줄에서 전역 context를 담는 필드 이름(예시의 app)은 미결정입니다.

직렬화 실패 처리

순환 참조나 BigInt가 있으면 JSON.stringify가 예외를 던집니다. 이를 잡아서 ctx를 {"_unserializable":"<이유>"}로 바꾸고 로그는 그대로 기록합니다. log()는 예외를 던지지 않습니다.

5. 세그먼트 파일명

active/   1793251200123_k3f9.seg
pending/  1793251200123_1793251260456_k3f9.seg
done/     1793251200123_1793251260456_k3f9.seg
          └ 시작 ts      └ 마지막 ts     └ tabId
  • 기록 중: {시작 ts}_{tabId}.seg
  • 봉인할 때: {시작 ts}_{마지막 ts}_{tabId}.seg로 이름을 바꿉니다. 봉인하면 어차피 move()로 디렉터리를 옮기므로 추가 비용이 없습니다.
  • ts는 13자리로 0을 채웁니다. 파일명을 문자열로 정렬하면 시간순이 됩니다(서기 2286년까지 유효).
  • tabId는 Worker가 시작할 때 무작위로 만드는 짧은 ID입니다.
  • 포맷 버전은 파일명에 넣지 않습니다. 파일 헤더에 있습니다.

이름만으로 할 수 있는 일

  • 쿼리: 시간 범위에 걸리는 파일만 엽니다.
  • 보존 정리: 오래된 순서와 기간 초과 여부를 판단합니다.
  • 주인 없는 파일 복구: Worker는 살아 있는 동안 opfslogd:tab:{tabId} Web Lock을 잡고 있습니다. 정리 담당은 navigator.locks.query()로 이 Lock이 없는 active/ 파일을 찾아 크래시 복구 후 봉인합니다.

6. 크래시 복구

  1. Worker가 세그먼트를 열 때, 파일 헤더 다음부터 프레임을 차례로 검사합니다.
  2. magic이 맞지 않거나, 남은 길이가 payload 길이보다 짧거나, CRC가 맞지 않는 첫 프레임을 찾습니다.
  3. 그 위치에서 파일을 잘라냅니다(handle.truncate()). 잃는 것은 마지막 flush 한 번분입니다.

7. 외부로 내보내는 포맷

  • export와 upload는 프레임 헤더를 걷어낸 순수 JSON Lines를 내보냅니다. 변환은 Worker에서 합니다.
  • 사용자와 백엔드는 내부 포맷을 몰라도 됩니다. 내부 포맷 버전을 올려도 외부에는 영향이 없습니다.
  • 업로드 meta.sha256은 변환된 JSONL을 기준으로 계산합니다. 서버가 실제로 받는 바이트와 같아야 검증할 수 있기 때문입니다.

8. 버전 호환

탭마다 라이브러리 버전이 다를 수 있고, 모든 탭이 같은 디렉터리를 씁니다. 다른 시스템의 방식을 참고했습니다.

참고배운 점적용
SQLite파일 헤더에 쓰기 버전과 읽기 버전을 따로 둠. 읽기 버전만 감당할 수 있으면 열 수 있음파일 헤더에 formatVersion과 minReaderVersion
Protobuf모르는 필드는 무시함. 필드를 추가해도 호환됨프레임 헤더에 headerLength. JSON 키 추가도 호환되는 변경
Kafka레코드 묶음마다 magic과 16비트 attributes. 압축 코덱 등을 비트로 표시프레임 헤더에 flags
IndexedDB새 버전이 열리면 이전 탭에 versionchange를 알림v0.1에는 필요 없음. 이전 탭은 모르는 파일을 건너뛰기만 하면 안전

규칙

  1. 파일명 규칙은 바꾸지 않습니다. 어떤 버전이든 이름만으로 시간 범위, 상태, 주인을 알 수 있어야 합니다.
  2. 쓰기는 항상 최신 포맷으로 합니다. 읽기는 이전 포맷도 모두 지원합니다. 0.x여도 지킵니다. 기기에 남은 pending 로그를 업그레이드 때문에 잃으면 안 되기 때문입니다.
  3. 헤더 끝에 필드를 추가하거나 JSON에 키를 추가하는 것은 호환되는 변경입니다. minReaderVersion을 올리지 않습니다.
  4. 정말로 호환이 깨지는 변경(예: payload 압축)일 때만 minReaderVersion을 올리거나 flags 비트를 씁니다.

이전 버전이 읽을 수 없는 파일을 만났을 때

작업동작이유
쿼리, export건너뛰고, 건너뛴 사실을 결과에 표시읽을 수 없음
보존 정리이름 기준으로 평소처럼 삭제파일명 규칙은 고정이므로 안전
업로드건너뛰고 pending에 둠. 새 버전 탭이 업로드JSONL로 변환할 수 없음
크래시 복구손대지 않음프레임 구조를 모름

9. 미결정 항목

  • 내보낸 JSONL에서 전역 context를 담는 필드 이름. 5단계 공개 API에서 init() 옵션 이름과 함께 정합니다.
  • 프레임 헤더와 파일 헤더의 바이트 배치. 필드 목록은 확정했고, 배치는 구현 단계에서 벤치마크와 함께 정합니다.

보류 (나중에 다시 검토)

  • 압축. 저장 시 압축(봉인 시 파일 전체 또는 프레임별), export와 upload의 gzip 옵션 모두 보류합니다. 보관 기간이 실제로 부족한지 측정한 뒤 판단합니다.
