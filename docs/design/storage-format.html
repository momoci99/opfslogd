opfslogd 저장 포맷

상태: 3단계 완료, 4단계에서 프레임 헤더 제거 · 최종 수정 2026-11-01 · 관련 결정: docs/decisions.md #010(대체됨), #011, #012, #013, #014, #016 · 상위 문서: architecture.html

세그먼트 파일은 JSON 헤더 한 줄과 그 뒤의 UTF-8 JSON Lines로 이루어진 텍스트 파일입니다. 바이너리 프레임은 쓰지 않습니다. 이 포맷은 라이브러리 내부 전용이며, 내보내기(export)와 업로드 때는 줄마다 탭 ID, seq, 전역 context를 채운 JSON Lines로 변환합니다.

1. 전제: 파일 포맷이 곧 전송 포맷

  • 메인 스레드는 log()를 호출할 때 레코드를 JSON.stringify로 직렬화해 둡니다(#014). flush할 때 이를 이어 붙여 바이트로 인코딩하고 Worker에 ArrayBuffer로 transfer합니다.
  • Worker는 받은 바이트에 다시 인코딩하지 않고 그대로 파일에 덧붙입니다.
  • 그래서 직렬화는 메인 스레드에서 한 번만 일어납니다. 객체를 그대로 postMessage로 보내면 structured clone(직렬화 1회)과 Worker 쪽 재인코딩(1회)으로 두 번이 됩니다.
  • 결국 포맷 선택은 "메인 스레드가 가장 싸게 인코딩할 수 있는 형태가 무엇인가"의 문제입니다.

2. 인코딩 방식

A. 순수 JSON LinesB. 순수 바이너리C. 바이너리 프레임 + JSON Lines
인코딩 속도빠름. 네이티브 JSON.stringify + TextEncoder.encodeInto고정 필드는 빠르지만, 임의 객체는 JS로 구현한 인코더가 필요A와 같음
런타임 의존성없음직접 구현하거나 의존성 추가없음
크기키 이름이 레코드마다 반복됨가장 작음 (약 20~30% 절약)A와 거의 같음
손상 감지잘림, 0 바이트, 파싱 실패를 줄 단위로 감지. 파싱되는 손상은 못 잡음길이와 CRC로 감지프레임마다 길이와 CRC32로 감지
쿼리 시 거르기파일명으로 파일 단위(#012). 파일 안에서는 줄 앞부분의 ts와 레벨을 문자열로 검사레코드 단위로 가능프레임 단위로 건너뜀 (시간 범위, 레벨 비트마스크)
판정채택 (2026-11-01, #016)탈락철회 (3단계에서 채택했다가 4단계에서 철회)

C안(프레임)을 철회한 이유

3단계에서는 JSONL의 약점 두 가지를 메우려고 프레임 헤더를 넣었습니다. "파싱은 되는 손상을 못 잡는다"와 "쿼리할 때 모든 줄을 파싱해야 한다"였습니다. 4단계에서 메인 스레드와 Worker 사이 프로토콜을 정하다가 이 두 근거를 다시 따져 봤습니다.

  • 손상: 크래시로 실제로 생기는 손상은 꼬리가 잘리거나 0으로 채워지는 것입니다. 줄 단위 검사로 잡힙니다. 줄 단위로 복구하면 쓰다 끊긴 flush 안의 온전한 줄도 살릴 수 있습니다. 프레임 방식은 그 flush를 통째로 버립니다.
  • 쿼리: 3단계 뒤에 정한 #012(파일명에 시간 범위)로 파일 단위 거르기가 이미 생겼습니다. 파일 안에서는 줄이 항상 {"ts":13자리,"lv":"로 시작하므로, 파싱하지 않고 문자열 위치만 보고 거를 수 있습니다.
  • 비용: 프레임이 있으면 flush마다 집계값 전달, 헤더 자리 확보, CRC 계산, 헤더 바이트 배치 설계가 필요합니다. 빼면 메인 스레드는 바이트를 보내고 Worker는 덧붙이기만 합니다.

다른 시스템 사례

구조사례프레임을 쓰는 이유
프레임 + 체크섬LevelDB/RocksDB WAL, SQLite WAL, Kafka, Vector 디스크 버퍼, Elastic Beats 디스크 큐내용이 바이너리(직렬화 객체, 압축, 암호화)라 줄바꿈으로 레코드를 나눌 수 없음. DB WAL은 손상된 레코드가 재생되면 DB가 깨짐
블록 헤더 (체크섬 확인 안 됨)Tencent Mars xlog (모바일 앱 로그)블록마다 압축하고 암호화하므로 블록 경계가 필요
체크섬 선택 사항Fluent Bit 파일 버퍼storage.checksum(CRC32) 기본값이 off
텍스트 줄Docker json-file, pino, winston, syslog프레임과 체크섬 없음

사례는 "내용이 바이너리, 압축, 암호화이면 프레임, 텍스트 줄이면 프레임 없음"으로 갈립니다. 압축이나 암호화를 나중에 넣게 되면 그때 프레임을 새 포맷 버전으로 추가합니다(#013).

레코드마다 바이너리 헤더를 붙이는 방식도 넣지 않습니다. 벤치마크에서 쿼리가 병목으로 나오면 포맷 버전을 올려 검토합니다.

3. 세그먼트 구조

헤더 줄 (초안)

키 이름은 초안이며 구현할 때 확정합니다. 레코드 줄은 {"ts":로 시작하므로 헤더 줄과 구별됩니다.

키용도
format이 파일을 쓴 포맷 버전 (#013의 formatVersion)
minReader읽는 데 필요한 최소 버전 (#013의 minReaderVersion)
tab탭 ID. 파일명에도 있지만 파일 하나만 꺼내 봐도 알 수 있게 둠
seq0이 파일 첫 줄의 seq. 같은 Worker의 이전 세그먼트에서 이어서 셈
context전역 context (#011)

규칙

  • 키 순서 고정: 레코드 줄은 항상 ts, lv 순서로 시작합니다. ts가 13자리 고정이라 레벨이 줄의 고정 위치에 오고, 쿼리가 JSON.parse 없이 거를 수 있습니다.
  • 헤더 줄은 항상 평문 JSON: 나중에 압축 같은 기능이 생겨도 헤더 줄은 그대로 둡니다. 어떤 버전이든 minReader를 읽고 이 파일을 건너뛸지 판단할 수 있어야 합니다.
  • 줄 경계: JSON.stringify는 문자열 안의 줄바꿈을 \n으로 이스케이프하므로, 레코드 내용이 줄 경계를 깨지 않습니다.

브라우저에서 파일에 쓰기

OPFS의 sync handle은 바이트(ArrayBuffer, TypedArray)만 받습니다. 텍스트도 TextEncoder로 바이트로 바꿔서 씁니다.

// 메인 스레드 (flush)
const payload = lines.join('\n') + '\n'
const buf = new Uint8Array(payload.length * 3)        // UTF-8 최대 크기
const { written } = new TextEncoder().encodeInto(payload, buf)
worker.postMessage(buf.buffer, [buf.buffer])           // + written

// Worker
handle.write(new Uint8Array(buffer, 0, written), { at: offset })

4. 레코드 스키마

내부 JSONL 한 줄의 형태입니다.

{"ts":1793251200123,"lv":"error","msg":"결제 실패","ctx":{"userId":42},"err":{"name":"TypeError","message":"…","stack":"…"}}
필드필수내용
ts✓Date.now() 밀리초 정수 (wall clock). 시계가 뒤로 갈 수 있으므로 탭 안 순서는 seq로 판단
lv✓"debug" · "info" · "warn" · "error"
msg✓문자열
ctx사용자 부가 정보. 별도 필드에 묶어서 예약 필드와 키가 충돌하지 않게 함
errError를 name, message, stack으로 풀어서 저장. JSON.stringify(new Error())는 {}가 되기 때문

레코드에 넣지 않고 헤더에 한 번만 두는 값

값위치이유
tab (탭 ID)헤더 줄세그먼트 하나는 탭 하나 소유
seq (탭 안 순번)헤더 줄의 seq0 + 줄 번호계산으로 복원 가능
전역 context (앱 버전, 세션 ID 등)헤더 줄init()에서 한 번 정해지는 값

export와 upload에서 JSONL로 변환할 때 이 값들을 각 줄에 다시 채워 넣습니다. 레코드마다 수십 바이트를 아끼며, 초당 1만 건이면 초당 수백 KB에 해당합니다.

// 내보낸 JSONL 한 줄
{"ts":1793251200123,"tab":"k3f9","seq":1042,"lv":"error","msg":"결제 실패","ctx":{"userId":42},"app":{"version":"2.3.1"}}

내보낸 줄에서 전역 context를 담는 필드 이름(예시의 app)은 미결정입니다.

직렬화 실패 처리

순환 참조나 BigInt가 있으면 JSON.stringify가 예외를 던집니다. 이를 잡아서 ctx를 {"_unserializable":"<이유>"}로 바꾸고 로그는 그대로 기록합니다. log()는 예외를 던지지 않습니다.

5. 세그먼트 파일명

active/   1793251200123_k3f9.seg
pending/  1793251200123_1793251260456_k3f9.seg
done/     1793251200123_1793251260456_k3f9.seg
          └ 시작 ts      └ 마지막 ts     └ tabId
  • 기록 중: {시작 ts}_{tabId}.seg
  • pending으로 옮길 때: {시작 ts}_{마지막 ts}_{tabId}.seg로 이름을 바꿉니다. 어차피 move()로 디렉터리를 옮기므로 이름도 함께 바꾸면 추가 비용이 없습니다.
  • ts는 13자리로 0을 채웁니다. 파일명을 문자열로 정렬하면 시간순이 됩니다(서기 2286년까지 유효).
  • tabId는 Worker가 시작할 때 무작위로 만드는 짧은 ID입니다.
  • 포맷 버전은 파일명에 넣지 않습니다. 파일 헤더에 있습니다.

이름만으로 할 수 있는 일

  • 쿼리: 시간 범위에 걸리는 파일만 엽니다.
  • 보존 정리: 오래된 순서와 기간 초과 여부를 판단합니다.
  • 주인 없는 파일 복구: Worker는 살아 있는 동안 opfslogd:tab:{tabId} Web Lock을 잡고 있습니다. 정리 담당은 navigator.locks.query()로 이 Lock이 없는 active/ 파일을 찾아 크래시 복구 후 pending으로 옮깁니다.

6. 크래시 복구

  1. 정리 담당 탭의 Worker가 주인 없는 active/ 세그먼트를 열고, 헤더 줄 다음부터 줄을 차례로 검사합니다.
  2. \n으로 끝나지 않거나, NUL 바이트가 있거나, 파싱되지 않는 첫 줄을 찾습니다.
  3. 그 줄의 시작 위치에서 파일을 잘라냅니다(handle.truncate()). 쓰다 끊긴 flush 안에서도 온전히 써진 줄은 살아남습니다.
  4. 헤더 줄 자체가 깨진 파일은 쓸 수 있는 레코드가 없으므로 삭제합니다.
중간의 나쁜 줄 하나만 건너뛰고 뒤를 살리지 않습니다. 그러면 뒤 줄들의 줄 번호가 밀려서 seq = seq0 + 줄 번호 계산이 틀어집니다. 첫 번째 나쁜 줄에서 잘라내기만 합니다.

잡지 못하는 것: 디스크에서 내용이 바뀌었는데 결과가 우연히 유효한 JSON인 경우입니다. 드물고, 결과는 로그 한 줄의 값이 틀리는 정도입니다. 파일이 닫힌 뒤(pending 이후)에는 업로드용 sha256(#007)이 있습니다.

7. 외부로 내보내는 포맷

  • export와 upload는 헤더 줄을 빼고, 줄마다 tab, seq, 전역 context를 채운 JSON Lines를 내보냅니다. 변환은 Worker에서 합니다.
  • 사용자와 백엔드는 내부 포맷을 몰라도 됩니다. 내부 포맷 버전을 올려도 외부에는 영향이 없습니다.
  • 업로드 meta.sha256은 변환된 JSONL을 기준으로 계산합니다. 서버가 실제로 받는 바이트와 같아야 검증할 수 있기 때문입니다.

8. 버전 호환

탭마다 라이브러리 버전이 다를 수 있고, 모든 탭이 같은 디렉터리를 씁니다. 다른 시스템의 방식을 참고했습니다.

참고배운 점적용
SQLite파일 헤더에 쓰기 버전과 읽기 버전을 따로 둠. 읽기 버전만 감당할 수 있으면 열 수 있음파일 헤더에 formatVersion과 minReaderVersion
Protobuf모르는 필드는 무시함. 필드를 추가해도 호환됨헤더 줄과 레코드 줄 모두 JSON이라 모르는 키는 무시. 키 추가는 호환되는 변경
Kafka레코드 묶음마다 magic과 16비트 attributes. 압축 코덱 등을 비트로 표시적용 안 함 (#016에서 프레임 제거). 호환되지 않는 기능은 minReader를 올려 표시
IndexedDB새 버전이 열리면 이전 탭에 versionchange를 알림v0.1에는 필요 없음. 이전 탭은 모르는 파일을 건너뛰기만 하면 안전

규칙

  1. 파일명 규칙은 바꾸지 않습니다. 어떤 버전이든 이름만으로 시간 범위, 상태, 주인을 알 수 있어야 합니다.
  2. 쓰기는 항상 최신 포맷으로 합니다. 읽기는 이전 포맷도 모두 지원합니다. 0.x여도 지킵니다. 기기에 남은 pending 로그를 업그레이드 때문에 잃으면 안 되기 때문입니다.
  3. 헤더 줄이나 레코드 줄에 JSON 키를 추가하는 것은 호환되는 변경입니다. minReader를 올리지 않습니다.
  4. 정말로 호환이 깨지는 변경(예: 압축, 암호화, 프레임 재도입)일 때만 minReader를 올립니다.

이전 버전이 읽을 수 없는 파일을 만났을 때

작업동작이유
쿼리, export건너뛰고, 건너뛴 사실을 결과에 표시읽을 수 없음
보존 정리이름 기준으로 평소처럼 삭제파일명 규칙은 고정이므로 안전
업로드건너뛰고 pending에 둠. 새 버전 탭이 업로드JSONL로 변환할 수 없음
크래시 복구손대지 않음줄 구조가 같다고 장담할 수 없음

9. 미결정 항목

  • 내보낸 JSONL에서 전역 context를 담는 필드 이름. 5단계 공개 API에서 init() 옵션 이름과 함께 정합니다.
  • 헤더 줄의 키 이름. 구현할 때 정합니다.

보류 (나중에 다시 검토)

  • 압축. 저장 시 압축(파일을 닫을 때 파일 전체, 또는 프레임을 다시 도입해 flush별), export와 upload의 gzip 옵션 모두 보류합니다. 보관 기간이 실제로 부족한지 측정한 뒤 판단합니다.
