메인 스레드 ↔ Worker 프로토콜

상태: 4단계 완료 · 최종 수정 2026-11-01 · 관련 결정: docs/decisions.md #014 ~ #023, 7단계 보완 #061, #064, #066, #067 · 상위 문서: architecture.html, storage-format.html

log()는 그 자리에서 레코드를 JSON 문자열로 만들어 메인 스레드의 문자열 큐에 넣습니다. 세 가지 조건 중 하나가 맞으면 큐를 바이트 하나로 묶어 Worker로 transfer하고, Worker는 받은 바이트를 세그먼트 파일에 그대로 덧붙입니다.

2. 직렬화 시점: log()를 호출할 때 (#014)

사용자 객체를 flush까지 들고 있지 않고, log()를 호출한 순간 JSON.stringify합니다.

flush 때 직렬화 (탈락)log() 때 직렬화 (채택)
기록되는 값flush 시점의 값. log('x', obj); obj.a = 2이면 2가 기록됨호출한 순간의 값
버퍼 상한JS에 sizeof가 없어 셀 수 없음문자열 길이로 셈
flush 순간 부하폭주 때 약 20,000건을 한 번에 직렬화. 수십 ms 멈춤비용이 호출마다 나뉨
log() 비용push 한 번JSON.stringify 한 번 (작은 객체 약 1µs, 측정 필요)
과부하 때 버리기쌓인 것 중 debug를 골라 뺌이미 직렬화한 것은 못 뺌. 새로 들어오는 낮은 레벨을 거절

3. 메인 스레드 버퍼: 문자열 큐 (#015)

log() 때:  strings.push(json); size += json.length

flush 때:  payload = strings.join('\n') + '\n'
           새 Uint8Array에 encodeInto(payload)
           Worker에 transfer
           strings = [], size = 0
  • 링버퍼를 쓰지 않습니다. transfer한 ArrayBuffer는 보낸 쪽에서 detach되어 다시 쓸 수 없습니다. 메모리를 공유하는 진짜 링버퍼는 SharedArrayBuffer가 필요하고, 이건 사이트에 COOP/COEP 헤더를 요구합니다. 라이브러리가 강요할 수 없습니다.
  • 예전 SharedWorker 설계에서는 GC를 줄이려고 링버퍼를 썼습니다. 지금 구조에서는 할당이 flush마다 버퍼 하나뿐이라 그럴 필요가 없습니다.
  • 크기는 문자열 길이(UTF-16 단위)로 셉니다. 메모리 상한이 목적이므로 디스크의 UTF-8 바이트 수와 달라도 됩니다.
  • 버퍼 풀(Worker가 쓴 버퍼를 돌려줘서 재사용)은 넣지 않습니다. 벤치마크에서 GC가 문제로 나오면 검토합니다.

4. flush 시점 (#017)

아래 조건 중 하나라도 맞으면 flush합니다. 숫자는 벤치마크에서 조정할 초안입니다.

트리거조건 (초안)이유
주기버퍼가 비어 있다가 첫 레코드가 들어오면 200ms 타이머를 건다
200ms는 근거 없는 초안. 아래 "주기 숫자를 정하는 기준" 참고		평소 크래시 때 잃는 양의 상한. 버퍼가 비어 있으면 타이머가 없어서, 로그가 없는 탭이 계속 깨어나지 않음(모바일 배터리)
크기버퍼가 256K자를 넘으면 바로폭주 때 상한에 닿기 전에 비움. flush 한 번의 join과 인코딩 비용, Worker로 가는 메시지 크기를 작게 유지
errorerror 레벨이 들어오면 마이크로태스크로 flush. 직전 flush 후 50ms가 지나지 않았으면 그 50ms 시점으로 미룸렌더러 크래시나 강제 종료 직전의 error를 덜 잃음. 같은 틱의 error는 한 번으로 묶이고, 여러 틱에 걸친 error 폭주에도 flush는 초당 최대 20번

주기 숫자를 정하는 기준

200ms는 1단계 성능 목표에 예시로 넣은 숫자이고 근거가 없습니다. 숫자는 벤치마크에서 다음 기준으로 고릅니다.

저사양 모바일에서 flush 비용이 메인 스레드 시간의 1% 이하인 가장 짧은 간격
  • 짧을수록 크래시 때 잃는 양이 줄어듭니다. 크래시를 조사할 때는 마지막 순간의 로그가 가장 중요합니다.
  • 길수록 flush 횟수가 줄어듭니다. 우리 flush는 네트워크가 아니라 같은 탭의 Worker로 넘기는 것이라 수십 µs 수준으로 추정합니다(미측정). 그렇다면 200ms보다 짧게 잡을 수 있습니다.
  • 타이머는 버퍼에 로그가 있을 때만 걸리므로, 간격을 줄여도 로그가 없는 탭의 배터리 문제는 없습니다.
다른 시스템 (기억에 근거)모으는 간격맥락
Logback, Log4j2 비동기없음같은 프로세스. 백그라운드 스레드가 큐를 계속 비움
Kafka producer linger.ms5ms (4.0부터)처리량을 위해 짧게 묶음
OpenTelemetry 로그 배치, Fluent Bit1초네트워크 전송. 요청 수를 줄이는 게 목적
Tencent Mars, Meituan Logan (모바일)거의 없음mmap으로 프로세스가 죽어도 OS가 내용을 남김. 브라우저에는 없는 방법

크기 트리거가 필요한 이유

주기만 있으면 1단계의 폭주 목표(1초에 100,000건)에서 200ms마다 약 20,000건, 레코드당 약 200자로 잡으면 약 4M자가 쌓입니다. 버퍼 상한(초안 4MB)에 한 주기 만에 닿습니다. 그러면 Worker는 놀고 있는데 다음 주기를 기다리느라 로그를 버리게 됩니다. 그 4M자를 한 번에 join하고 인코딩하는 비용도 메인 스레드에 몰립니다.

error 트리거의 효과 범위

탭을 닫거나 다른 페이지로 이동하는 경우는 pagehide 처리가 맡습니다. JS 에러로 탭이 죽지는 않습니다. 그래서 error 즉시 flush가 실제로 도움이 되는 건 렌더러 크래시(OOM 등)나 강제 종료 직전입니다. 효과 범위는 좁지만 비용이 작아서 넣습니다.

여기서 다루지 않는 트리거

  • 페이지가 숨겨지거나 닫힐 때(visibilitychange, pagehide): 아래 남은 항목에서 다룹니다. 백그라운드 탭은 타이머가 1초에 한 번(Chrome은 오래 숨겨지면 1분에 한 번)으로 늦춰지므로 주기 트리거만으로는 부족합니다.
  • 사용자가 직접 부르는 flush(): 5단계에서 정했습니다(#038).
크기 트리거로 드러난 문제 (#018에서 해결): 크기 트리거가 있으면 메인 스레드 버퍼는 256K자 이상 쌓이지 않으므로, 버퍼에 건 4MB 상한은 발동하지 않습니다. 하지만 Worker가 OPFS 쓰기를 따라가지 못하면 보낸 메시지가 Worker의 메시지 큐에 쌓입니다. 메인 스레드는 그 양을 볼 수 없고, 큐에는 상한도 없습니다. 상한은 "메인 버퍼 + 보냈지만 아직 쓰지 않은 양"에 걸어야 합니다. 그래서 Worker가 쓰기 완료 응답(ack)을 보내도록 했습니다. 다음 절을 보세요.

5. Worker 응답과 버퍼 상한 (#018)

Worker는 flush 하나를 파일에 쓴 뒤 그 flush의 id를 메인 스레드로 돌려보냅니다. 메인 스레드는 응답이 오지 않은 양(inFlight)을 세고, 상한은 "메인 버퍼 + inFlight"에 겁니다.

메인 스레드                                   Worker
───────────                                   ──────
flush #41 (12K자)
  inFlight += 12K
  worker.postMessage({ id: 41, buf, lines, minTs, maxTs }, [buf]) ──▶  onmessage
                                                  handle.write(buf)
                                     ◀────────── self.postMessage({ id: 41, ok: true })
worker.onmessage
  inFlight -= 12K   (보낼 때 41번 크기를 기억해 둠)

7단계에서 더한 것: lines(줄 수)는 Worker가 다음 세그먼트의 seq0를 정할 때(#064), minTs, maxTs는 파일명의 시간 범위에(#067) 씁니다. 쓰기가 실패하면 Worker는 쓰기 전 위치로 되돌리고 ok: false로 응답한 뒤 로테이션합니다. 메인은 그 flush의 줄 수를 drop으로 셉니다(#064).

A. 응답 없음B. flush마다 ack (채택)C. Worker 쪽에서 버림
상한메인 버퍼에만 걸림. 사실상 없음메인 버퍼 + inFlight. 실제 메모리 상한이 됨버릴 때는 이미 메모리를 쓴 뒤
레벨별 거절 (#014)동작 안 함메인에서 동작Worker가 다시 파싱해야 함
비용없음작은 메시지 하나. 평소 초당 약 5번없음
  • Worker가 밀리는 경우: 같은 Worker가 export와 업로드용 JSONL 변환, 크래시 복구도 합니다. 그동안 쓰기 메시지는 줄을 섭니다. 모바일에서는 OPFS 쓰기 자체가 느릴 수도 있습니다.
  • Worker → 메인 채널은 이미 있습니다: 업로드 Blob 전달(#007), 오류 알림. ack는 메시지 종류 하나를 더하는 것입니다.
  • 덤: 응답이 끊기면 Worker가 죽었거나 멈췄다는 것을 메인이 알 수 있습니다.
  • 주의: 메인 스레드가 긴 작업을 하는 동안 ack는 처리되지 않으므로 inFlight가 실제보다 크게 보입니다. 결과는 일찍 거절하는 쪽(안전한 방향)으로 틀립니다. 거절 문턱을 정할 때 고려합니다.

6. 과부하 때 버리기 (#019)

과부하는 들어오는 속도를 디스크 쓰기가 따라가지 못해, 아직 디스크에 가지 않은 양(메인 버퍼 + 응답 안 온 양)이 쌓인 상태입니다. 초당 건수가 많아도 Worker가 따라가면 과부하가 아닙니다.

버린다는 것은 새로 들어온 로그를 저장하지 않고 그 자리에서 없애는 것입니다. 이미 버퍼나 디스크에 있는 로그는 건드리지 않습니다. 디스크의 오래된 세그먼트를 지우는 보존 정리(#007)와는 다른 일입니다.

사용량 (메인 버퍼 + 응답 안 온 양)받는 것거절하는 것
80% 미만전부없음
80% 이상warn, errordebug, info
100%없음전부 (error 포함)
log.debug('스크롤 위치', { y: 120 })
// 1. 사용량 확인 → 85% → debug는 거절
// 2. dropped.debug += 1
// 3. 바로 return. JSON.stringify도 하지 않음 (거절된 log()는 더 쌈)

검토한 안

S0. 상한 없음S1. 상한 하나, 레벨 무관S2. 두 단계 (채택)
사례winstonOpenTelemetry, Sentry, sonic-boomLogback AsyncAppender (남은 공간 20% 미만이면 TRACE/DEBUG/INFO 버림)
폭주 중 error지킴 (탭이 안 죽는 한)debug 폭주가 상한을 채우면 error도 버림남은 20%로 지킴
메모리끝없이 늘 수 있음. 탭이 죽으면 전부 잃음상한 지킴상한 지킴
  • 왜 레벨을 보나: 과부하는 대개 낮은 레벨의 폭주(반복문 안의 debug 등)에서 생기고, 무언가 잘못되는 순간과 겹치는 경우가 많습니다. 레벨을 보지 않으면 그때의 error를 잃습니다.
  • 문턱은 정확하지 않습니다: ack 지연(#018), 글자 수와 실제 메모리의 차이, 임의로 정한 상한 때문에 80%와 100%는 "대략 그쯤"입니다. S2에 필요한 것은 정확한 지점이 아니라 "낮은 레벨이 먼저 막힌다"는 순서뿐이므로, 문턱이 흔들려도 목적은 유지됩니다.
  • 기다리기(block)는 못 씁니다: Logback과 Log4j2의 기본값은 큐가 차면 로그를 찍은 스레드를 멈추는 것입니다. log()는 메인 스레드에서 돌기 때문에 멈추면 화면이 멈춥니다.
  • 100%에서는 error도 버립니다: 끝까지 받으면 메모리가 계속 늘어 탭이 죽을 수 있고, 그러면 전부 잃습니다.
  • 50/75/90/100% 네 단계 안은 사례가 없고 맞출 숫자만 늘어나서 뺐습니다.

버린 건수 기록

버릴 때마다 레벨별 숫자만 셉니다. 다음 flush에서 숫자가 0이 아니면 맨 끝에 한 줄을 붙이고 카운터를 0으로 되돌립니다. 필드 이름은 초안입니다.

{"ts":1793251200400,"lv":"warn","msg":"opfslogd: records dropped","ctx":{"reason":"overload","dropped":{"debug":1200,"info":300},"from":1793251200210,"to":1793251200390}}
  • flush마다 최대 한 줄이라 이 줄이 폭주하지 않습니다.
  • 일반 레코드와 같은 형태라 export와 업로드가 따로 처리할 필요가 없습니다. seq도 하나 차지합니다.
  • from, to는 처음과 마지막으로 버린 시각입니다. 읽는 사람이 이 구간에 빈 곳이 있다는 것을 알 수 있습니다.
  • journald가 로그 안에 "Suppressed N messages" 줄을 남기는 것과 같은 방식입니다. reason은 Sentry처럼 이유를 구분하려고 둡니다. 다른 이유도 같은 형식으로 남깁니다: "retention"(보존 정리로 지운 pending 세그먼트, #050), "quota"와 "write-failed"(쓰기 실패, #064).
  • 모든 레코드 줄은 메인 스레드의 flush에서 나옵니다(#061). Worker에서 생긴 사건(retention 삭제)은 건수만 메인에 보내고, 메인이 다음 flush에서 drop 줄로 씁니다. 그래야 메인이 센 seq와 파일의 줄 번호가 맞습니다. tabId도 메인이 만듭니다.
  • 앱에 따로 알리는 콜백은 두지 않습니다(#039). drop 줄을 알아보는 방법은 #044입니다.

7. 숨겨질 때와 닫힐 때 (#020)

신호언제하는 일
visibilitychange → hidden탭 전환, 창 최소화, 모바일 앱 전환, 닫기 직전바로 flush. 페이지와 Worker가 아직 살아 있어 쓰기까지 정상적으로 됨
pagehide닫기, 다른 페이지로 이동바로 flush. Worker도 같이 종료되므로 쓰일지 장담할 수 없음 (최선)
(신호 없음)모바일에서 백그라운드 앱을 OS가 종료할 수 있는 일 없음. 그래서 hidden 때 flush가 중요
  • 로테이션 시점은 크기(초안 2MB, #066)와 시간(초안 5분)입니다(#021). 오래 열어 둔 탭도 업로드 주기에 맞춰 로그가 올라가게 하려는 것입니다. 시간 상한은 공개 옵션 rotate.maxAgeMs입니다(#036).
  • 닫힐 때 pending으로 옮기지 않습니다. 이 작업은 Worker 안의 비동기 작업(handle 닫기, move())이라 페이지가 사라지는 중에는 끝까지 실행된다는 보장이 없습니다. 탭이 사라지면 그 탭의 Lock(opfslogd:{ns}:tab:{tabId}, #034)이 풀리고, 정리 담당 탭이 주인 없는 active/ 파일을 복구하고 pending으로 옮깁니다(#012). 정상 종료와 크래시가 같은 경로로 처리됩니다.
  • hidden 때도 로테이션하지 않습니다. 탭을 자주 전환하면 작은 세그먼트가 수없이 생깁니다.
  • 숨겨진 동안의 타이머: 백그라운드 탭의 타이머는 약 1초, Chrome에서 오래 숨겨지면 1분까지 늦어집니다. 그래서 log()가 호출될 때 버퍼의 첫 레코드가 flush 주기보다 오래됐으면 바로 flush합니다. 마지막 로그 뒤에 호출이 없으면 늦어진 타이머를 기다립니다.

8. 같은 탭 안 구독 subscribe() (#023)

subscribe(fn)는 로그가 기록될 때마다 앱이 등록한 함수에 그 로그를 알려주는 통로입니다. 저장된 로그를 나중에 꺼내는 exportLogs()와 달리 지금 막 기록된 로그를 받습니다. 같은 탭 안에서만 동작합니다(#006). v0.1에 포함합니다.

  • 쓰임: 앱 안의 디버그 패널(DevTools를 열기 어려운 모바일 등), 개발 중 콘솔 출력, 테스트
  • 부르는 때: flush 때 묶음을 만든 뒤, Worker로 보내기 전에 구독 함수마다 한 번씩 그 묶음을 넘깁니다.
  • 받는 내용: 파일에 들어가는 것과 같습니다. 거절된 로그는 오지 않고, 버린 건수 줄(#019)은 옵니다.
  • 구독 함수가 예외를 던져도 격리되어 로그 저장에 영향이 없습니다. 구독자가 없으면 추가 비용은 0입니다.
  • 넘기는 형태는 export 줄과 같은 모양의 파싱된 객체 배열이고, 해제는 반환된 함수로 합니다(#042, #043).

9. 5단계와 7단계에서 정한 것

  • subscribe()가 넘기는 형태와 API 모양 (#023 → #042, #043)
  • 버린 건수를 앱에 알리는 콜백 (#019 → #039, 없음)
  • 사용자가 직접 부르는 flush() (#017 → #038)
  • 세그먼트 시간 상한 옵션의 이름과 위치 (#021 → #036, rotate.maxAgeMs)
  • send()가 끝나지 않을 때를 위한 AbortSignal 또는 timeout (#022 → #045)
  • tab, seq를 누가 정하는가 (7단계 → #061), 쓰기 실패 처리 (→ #064), 파일명 시간의 뜻 (→ #067)
