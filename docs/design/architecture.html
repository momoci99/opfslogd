opfslogd 아키텍처

상태: 7단계에서 뒤 결정에 맞춰 갱신 · 최종 수정 2026-11-01 · 관련 결정: docs/decisions.md #006, #007, #009, #022, #034, #046, #050 ~ #053, #057, #059, #062, #065 ~ #068

각 탭이 자기 전용 Dedicated Worker로 자기 OPFS 파일에 로그를 씁니다. 탭끼리 로그를 주고받지 않으며, 여러 탭 중 하나만 해야 하는 일(보존 정리, 업로드)은 Web Locks로 조율합니다. SharedWorker는 사용하지 않습니다.

1. 요구사항

항목결정
대상 브라우저최신 2버전 데스크톱 + 모바일 (Chrome, Edge, Firefox, Safari, Android Chrome, iOS Safari)
로그량매우 높음. 초당 수천 건 이상
꺼내 쓰기파일 내보내기, 서버 업로드, 같은 탭 안 실시간 구독. 쿼리 API는 v0.1에서 뺐습니다(#057)
보존설정으로 조정. 기본값은 용량 상한 + 기간 상한

라이브러리라서 생기는 요구사항

  • import만으로 부작용 없음. Worker는 init()을 호출할 때 시작합니다. 브라우저 페이지가 아니면(SSR, Node 등) 아무것도 하지 않습니다(#062).
  • 버전 공존. 탭마다 라이브러리 버전이 다를 수 있습니다. 파일 헤더 줄에 포맷 버전을 넣습니다(#013). Lock 이름에는 버전을 넣지 않습니다. 버전이 달라도 같은 디렉터리와 Lock을 함께 씁니다(#034).
  • 번들러 호환. new URL('./worker.js', import.meta.url) 패턴은 Vite 8의 dev와 build에서 확인했습니다. 한 식으로 써야 합니다(#059). webpack 등 다른 번들러는 아직 확인하지 않았습니다.
  • Worker 배포. Worker는 별도 파일(dist/worker.js)로 배포하고 new URL('./worker.js', import.meta.url)로 불러옵니다. 번들러가 이 파일을 내보내지 못하거나(Rollup, esbuild) 라이브러리를 CDN에서 불러오는 경우, 사용자가 파일을 자기 origin에 두고 init({ workerUrl })로 경로를 넘깁니다. 인라인 빌드는 보류합니다(결정 #009).
  • 앱을 깨뜨리지 않음. 지원하지 않는 환경, 용량 부족, 오류가 생기면 조용히 축소 동작하고, 오류는 콜백으로만 알립니다.
  • 네임스페이스. 같은 origin 안의 여러 앱이나 인스턴스는 디렉터리로 분리합니다.

2. 성능 목표

첫 기준값입니다. 벤치마크로 측정하면서 점진적으로 조정합니다.

항목목표
지속 처리량origin 전체 초당 10,000건 (데스크톱)
순간 폭주1초에 100,000건이 들어와도 크래시 없음. 버리는 것은 허용하되 버린 건수를 기록
log() 비용메인 스레드를 막지 않고 예외도 던지지 않음. 평균 수 µs 이하
메모리탭당 버퍼 상한(예: 4MB). 넘치면 정해진 정책대로 버림
유실 구간크래시 시 최대 flush 주기만큼. 주기는 벤치마크로 정함(protocol.html, 초안 200ms). 페이지를 닫을 때(pagehide)는 가능한 한 flush
과부하 시 버리는 순서debug, info를 먼저 거절하고 warn, error는 상한까지 받음. 상한(100%)에서는 error도 거절(#019). 버린 건수는 별도 레코드로 남김
포기한 것: 유실 0 보장(메인 스레드에서는 동기로 쓸 수 없음), 탭 간 완전한 순서, 레코드마다 쿼리 색인 갱신.

3. 검토한 구조

안구조판정이유
ASharedWorker가 createWritable()로 기록탈락비동기 쓰기라 이 로그량을 감당하기에 느림
BSharedWorker 안에 Dedicated Worker를 띄워 sync handle 사용탈락SharedWorker 안의 중첩 Worker는 Chrome 지원이 불확실
CWeb Locks로 리더 탭을 뽑고, 다른 탭은 BroadcastChannel로 로그 전달비추천모든 탭에 메시지가 복사되고, 리더 하나가 병목이 되며, 리더가 죽으면 그 버퍼를 잃음
DC와 같지만 SharedWorker가 MessagePort 연결을 중개가능리더 교체, 재연결, Android에서의 SharedWorker 종료를 모두 처리해야 해서 복잡
E탭마다 Dedicated Worker가 자기 파일에 기록채택쓰기 경로에 탭 간 통신이 없고, 탭이 늘면 처리량도 늘며, 장애가 그 탭 안에서 끝남

판단 근거가 된 사실

  • createSyncAccessHandle()은 Dedicated Worker에서만 쓸 수 있습니다.
  • Android Chrome의 SharedWorker는 Chrome 148(2026)에서 다시 켜졌습니다. 앱이 백그라운드로 가면 SharedWorker 인스턴스가 종료될 수 있습니다.
  • sync access handle은 파일 하나에 하나만 열 수 있습니다. 그래서 파일마다 쓰는 쪽이 하나뿐이어야 합니다.
  • BroadcastChannel로는 MessagePort를 넘길 수 없습니다.
  • 과거 설계에서 SharedWorker를 쓴 주된 이유는 업로드를 한 곳에서만 하기 위해서였습니다. 이 역할은 Web Locks로 대체합니다.

4. 선택한 구조

쓰기 경로

  1. log()는 레코드를 JSON 문자열로 만들어 메인 스레드의 문자열 큐에 넣습니다(#014, #015). postMessage는 매번 하지 않습니다.
  2. 버퍼가 찼거나 flush 주기가 되면 레코드를 하나의 ArrayBuffer로 묶어 Worker에 transfer합니다(복사 없음).
  3. Worker는 sync handle로 자기 active 세그먼트에 덧붙입니다.
  4. 세그먼트가 상한 크기(초안 2MB, #066)에 도달하거나, 열린 지 일정 시간(초안 5분)이 지났고 비어 있지 않으면 로테이션합니다: 지금 파일을 닫아 pending/ 또는 done/으로 옮기고 새 파일을 엽니다(#021). 오래 열어 둔 탭의 로그도 업로드 주기에 맞춰 올라가게 하려는 것입니다.
  5. 탭이 닫힐 때는 pending으로 옮기지 않습니다. 탭의 Lock이 풀리면 정리 담당 탭이 주인 없는 active/ 파일을 복구하고 pending으로 옮깁니다(#012, #020).

읽기 경로 (내보내기)

닫힌 세그먼트 전부와 내 탭의 활성 세그먼트를 ts 기준으로 병합해서 읽습니다. 한 탭 안에서는 seq 순서를 지킵니다(#054, #056). 파일명에 든 시간 범위(그 파일 레코드 ts의 최솟값과 최댓값, #067)로 필요 없는 파일은 건너뜁니다.

실시간 구독

같은 탭 안에서만 지원합니다(subscribe(fn), #042 ~ #044). 탭 간 실시간 구독은 사용 사례가 없어 범위에서 뺐습니다.

설정 충돌

탭마다 init(config)을 호출합니다. 탭끼리 설정이 다르면, Lock을 잡은 탭이 자기 설정으로 정리와 업로드를 합니다. 세그먼트를 pending/과 done/ 중 어디로 보낼지는 그 세그먼트를 닫는 탭의 upload 설정을 따릅니다. upload가 없던 동안 닫힌 세그먼트는 나중에 올라가지 않습니다(#068).

5. 세그먼트 생명주기

상태는 디렉터리로 나누고, 상태가 바뀌면 FileSystemHandle.move()로 이동합니다.

6. 업로드

라이브러리는 업로드 프로토콜을 정하지 않습니다. 사용자가 send()를 넘기고, 라이브러리는 언제, 무엇을, 몇 번 보낼지만 정합니다.

init({
  upload: {
    send: async (file, meta) => {
      const { url } = await api.requestUploadUrl(meta)   // 1. presigned URL 요청
      await fetch(url, { method: 'PUT', body: file })      // 2. S3에 PUT
      await api.confirmUploaded(meta.segmentId)            // 3. 완료 통보
    },
    intervalMs: 60_000,
  },
})
약속내용
resolve세그먼트를 done으로 옮김
rejectpending에 그대로 두고 다음 주기에 재시도. 백오프는 없고, 그 실행은 첫 실패에서 끝남(#046). 시간 초과는 upload.timeoutMs(#045)
전달 보장최소 한 번(at-least-once). 서버는 segmentId로 중복을 걸러야 함
metasegmentId, sha256, size, from/to 시간, signal (#048)
업로더주기마다 각 탭이 opfslogd:{ns}:upload Lock을 ifAvailable로 잡아 봄. 잡은 탭이 pending을 올리고 바로 놓음. 못 잡은 탭은 이번 주기를 건너뜀 (#022)
file내부 세그먼트가 아니라 순수 JSON Lines로 변환한 Blob. 백엔드는 내부 포맷을 몰라도 됨 (#007, #033)
실행 위치함수는 Worker로 넘길 수 없어서, Lock을 가진 탭의 메인 스레드에서 실행. Worker가 파일을 읽어 Blob으로 넘김
멈춘 탭 문제 (#022에서 해결): 브라우저는 오래 숨겨진 탭을 멈추고(freeze), 멈춘 탭은 Lock을 계속 쥡니다. 예전 설계처럼 업로더가 Lock을 계속 쥐고 있으면 업로드가 전부 멈춥니다. 그래서 업로드와 보존 정리 Lock은 한 번 실행할 때만 잡고 바로 놓습니다. 멈춘 탭은 타이머가 돌지 않아 Lock을 시도하지도 않습니다. 탭 상태(visible/hidden)에 따른 조건은 두지 않습니다. 남는 위험은 실행 도중에 멈추는 경우로, 그 탭이 깨어날 때까지 그 한 번이 늦어집니다.

7. 보존 정책

옵션과 기본값은 api.html에서 정했습니다(#050 ~ #053).

retention: {
  maxBytes: 50_000_000,       // 50MB 초안, namespace 안 세그먼트 파일의 합계 (#052)
  maxAgeMs: 7 * 86_400_000,   // 7일 (#051)
}
  • 기간을 넘은 닫힌 세그먼트를 먼저 지우고, 그래도 합계가 넘으면 done의 오래된 것부터, 그다음 pending의 오래된 것부터 지웁니다(#050). 지운 pending은 drop 줄로 남깁니다.
  • OPFS는 파일 앞부분을 잘라낼 수 없어서, 세그먼트 파일을 통째로 지우는 방식이 가장 저렴합니다. 세그먼트 크기 상한(초안 2MB)은 내부값입니다(#035, #066).
  • navigator.storage.persist()는 호출하지 않고 옵션도 두지 않습니다. 필요한 앱이 직접 호출합니다(#065).

9. 검증할 것

결과는 benchmark.html에 모읍니다.

항목왜 필요한가상태
OPFS 디렉터리 안에서 FileSystemHandle.move()의 브라우저별 지원세그먼트 상태 전이에 사용세 엔진 모두 됨
다른 Worker가 sync handle을 연 파일을 getFile()로 읽을 수 있는가다른 탭의 active 세그먼트를 export에 넣을 수 있는지세 엔진 모두 읽힘. 쓰는 중 읽기는 미확인(#054 메모)
Web Lock을 가진 탭이 freeze되는가, 브라우저별로 언제 freeze되는가실행 도중 멈춤이 얼마나 자주 생기는지 (#022)실기기 목록
Vite dev 모드에서 Worker 경로가 깨지는가 (optimizeDeps.exclude 필요 여부)가장 흔한 사용 환경의 개발 경험설정 없이 됨. 단 한 식으로 써야 함(#059)
Worker 하나당 메모리 비용탭이 많을 때 비용구현 단계
모바일 Safari의 OPFS quota와 eviction 동작보존 기본값 검증실기기 목록
