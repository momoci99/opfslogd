opfslogd 아키텍처

상태: 설계 중 · 최종 수정 2026-10-29 · 관련 결정: docs/decisions.md #006, #007, #008, #009, #010

각 탭이 자기 전용 Dedicated Worker로 자기 OPFS 파일에 로그를 씁니다. 탭끼리 로그를 주고받지 않으며, 여러 탭 중 하나만 해야 하는 일(보존 정리, 업로드)은 Web Locks로 조율합니다. SharedWorker는 사용하지 않습니다.

1. 요구사항

항목결정
대상 브라우저최신 2버전 데스크톱 + 모바일 (Chrome, Edge, Firefox, Safari, Android Chrome, iOS Safari)
로그량매우 높음. 초당 수천 건 이상
꺼내 쓰기파일 내보내기, 쿼리 API, 서버 업로드, 같은 탭 안 실시간 구독
보존설정으로 조정. 기본값은 용량 상한 + 기간 상한

라이브러리라서 생기는 요구사항

  • import만으로 부작용 없음. SSR에서 import해도 동작해야 합니다. Worker는 init()을 호출할 때 시작합니다.
  • 버전 공존. 탭마다 라이브러리 버전이 다를 수 있습니다. 파일 포맷과 Lock 이름에 버전을 넣습니다.
  • 번들러 호환. new URL('./worker.js', import.meta.url) 패턴을 Vite, webpack, Rollup, esbuild에서 확인해야 합니다.
  • Worker 배포. Worker는 별도 파일(dist/worker.js)로 배포하고 new URL('./worker.js', import.meta.url)로 불러옵니다. 번들러가 이 파일을 내보내지 못하거나(Rollup, esbuild) 라이브러리를 CDN에서 불러오는 경우, 사용자가 파일을 자기 origin에 두고 init({ workerUrl })로 경로를 넘깁니다. 인라인 빌드는 보류합니다(결정 #009).
  • 앱을 깨뜨리지 않음. 지원하지 않는 환경, 용량 부족, 오류가 생기면 조용히 축소 동작하고, 오류는 콜백으로만 알립니다.
  • 네임스페이스. 같은 origin 안의 여러 앱이나 인스턴스는 디렉터리로 분리합니다.

2. 성능 목표

첫 기준값입니다. 벤치마크로 측정하면서 점진적으로 조정합니다.

항목목표
지속 처리량origin 전체 초당 10,000건 (데스크톱)
순간 폭주1초에 100,000건이 들어와도 크래시 없음. 버리는 것은 허용하되 버린 건수를 기록
log() 비용메인 스레드를 막지 않고 예외도 던지지 않음. 평균 수 µs 이하
메모리탭당 버퍼 상한(예: 4MB). 넘치면 정해진 정책대로 버림
유실 구간크래시 시 최대 flush 주기(예: 200ms)만큼. 페이지를 닫을 때(pagehide)는 가능한 한 flush
과부하 시 버리는 순서debug부터 버리고 error는 끝까지 보존. 버린 건수는 별도 레코드로 남김
포기한 것: 유실 0 보장(메인 스레드에서는 동기로 쓸 수 없음), 탭 간 완전한 순서, 레코드마다 쿼리 색인 갱신.

3. 검토한 구조

안구조판정이유
ASharedWorker가 createWritable()로 기록탈락비동기 쓰기라 이 로그량을 감당하기에 느림
BSharedWorker 안에 Dedicated Worker를 띄워 sync handle 사용탈락SharedWorker 안의 중첩 Worker는 Chrome 지원이 불확실
CWeb Locks로 리더 탭을 뽑고, 다른 탭은 BroadcastChannel로 로그 전달비추천모든 탭에 메시지가 복사되고, 리더 하나가 병목이 되며, 리더가 죽으면 그 버퍼를 잃음
DC와 같지만 SharedWorker가 MessagePort 연결을 중개가능리더 교체, 재연결, Android에서의 SharedWorker 종료를 모두 처리해야 해서 복잡
E탭마다 Dedicated Worker가 자기 파일에 기록채택쓰기 경로에 탭 간 통신이 없고, 탭이 늘면 처리량도 늘며, 장애가 그 탭 안에서 끝남

판단 근거가 된 사실

  • createSyncAccessHandle()은 Dedicated Worker에서만 쓸 수 있습니다.
  • Android Chrome의 SharedWorker는 Chrome 148(2026)에서 다시 켜졌습니다. 앱이 백그라운드로 가면 SharedWorker 인스턴스가 종료될 수 있습니다.
  • sync access handle은 파일 하나에 하나만 열 수 있습니다. 그래서 파일마다 쓰는 쪽이 하나뿐이어야 합니다.
  • BroadcastChannel로는 MessagePort를 넘길 수 없습니다.
  • 과거 설계에서 SharedWorker를 쓴 주된 이유는 업로드를 한 곳에서만 하기 위해서였습니다. 이 역할은 Web Locks로 대체합니다.

4. 선택한 구조

쓰기 경로

  1. log()는 레코드를 JSON 문자열로 만들어 메인 스레드의 문자열 큐에 넣습니다(#014, #015). postMessage는 매번 하지 않습니다.
  2. 버퍼가 찼거나 flush 주기가 되면 레코드를 하나의 ArrayBuffer로 묶어 Worker에 transfer합니다(복사 없음).
  3. Worker는 sync handle로 자기 active 세그먼트에 덧붙입니다.
  4. 세그먼트가 상한 크기(기본 8MB)에 도달하거나 탭이 닫히면 봉인하고 pending/ 또는 done/으로 옮깁니다.

읽기 경로 (내보내기, 쿼리)

모든 탭의 세그먼트를 ts와 탭별 seq 기준으로 병합 정렬해서 읽습니다. 세그먼트 파일명에 시간 범위를 넣어 쿼리할 때 필요 없는 파일은 건너뜁니다.

실시간 구독

같은 탭 안에서만 지원합니다(logger.subscribe(fn)). 탭 간 실시간 구독은 사용 사례가 없어 범위에서 뺐습니다.

설정 충돌

탭마다 init(config)을 호출합니다. 탭끼리 설정이 다르면, Lock을 잡은 탭이 자기 설정으로 정리와 업로드를 합니다.

5. 세그먼트 생명주기

상태는 디렉터리로 나누고, 상태가 바뀌면 FileSystemHandle.move()로 이동합니다.

6. 업로드

라이브러리는 업로드 프로토콜을 정하지 않습니다. 사용자가 send()를 넘기고, 라이브러리는 언제, 무엇을, 몇 번 보낼지만 정합니다.

init({
  upload: {
    send: async (file, meta) => {
      const { url } = await api.requestUploadUrl(meta)   // 1. presigned URL 요청
      await fetch(url, { method: 'PUT', body: file })      // 2. S3에 PUT
      await api.confirmUploaded(meta.segmentId)            // 3. 완료 통보
    },
    intervalMs: 60_000,
  },
})
약속내용
resolve세그먼트를 done으로 옮김
rejectpending에 그대로 두고 백오프 후 재시도
전달 보장최소 한 번(at-least-once). 서버는 segmentId로 중복을 걸러야 함
metasegmentId, sha256, size, from/to 시간, 레코드 수
업로더opfslogd:upload Lock을 잡은 탭 하나. 그 탭이 닫히면 Lock이 자동으로 풀리고 다른 탭이 이어받음
file내부 세그먼트가 아니라 순수 JSON Lines로 변환한 Blob. 백엔드는 내부 포맷을 몰라도 됨 (결정 #010)
실행 위치함수는 Worker로 넘길 수 없어서, Lock을 가진 탭의 메인 스레드에서 실행. Worker가 파일을 읽어 Blob으로 넘김
위험: 백그라운드에서 멈춘(frozen) 탭이 Lock을 쥔 채로 있으면 업로드가 멈춥니다. 대응 후보는 화면에서 숨겨질 때(visibilitychange → hidden) Lock을 내려놓고 보이는 탭이 우선 업로드하게 하는 것입니다. 상세 설계는 아직 하지 않았습니다.

7. 보존 정책

retention: {
  maxBytes: 100 * 1024 * 1024,        // 100MB, storage.estimate() quota의 10%를 넘지 않게 제한
  maxAgeMs: 7 * 24 * 60 * 60 * 1000,  // 7일
  segmentBytes: 8 * 1024 * 1024,      // 8MB, 삭제는 세그먼트 단위
}
  • 두 조건 중 먼저 걸리는 쪽이 적용됩니다. 초당 0.5~1MB가 쌓일 수 있어서 실제로는 용량 상한이 먼저 걸립니다.
  • 삭제 순서: done의 오래된 것부터, 그다음 pending의 오래된 것부터(롤링). 버린 건수를 기록합니다.
  • OPFS는 파일 앞부분을 잘라낼 수 없어서, 세그먼트 파일을 통째로 지우는 방식이 가장 저렴합니다.
  • navigator.storage.persist()는 기본으로 호출하지 않습니다. 사용자가 옵션으로 켭니다.

9. 검증할 것

항목왜 필요한가
OPFS 디렉터리 안에서 FileSystemHandle.move()의 브라우저별 지원세그먼트 상태 전이에 사용
다른 Worker가 sync handle을 연 파일을 getFile()로 읽을 수 있는가내보내기와 쿼리가 active 세그먼트를 읽을 수 있는지
Web Lock을 가진 탭이 freeze되는가업로드가 멈추는 위험
Vite dev 모드에서 Worker 경로가 깨지는가 (optimizeDeps.exclude 필요 여부)가장 흔한 사용 환경의 개발 경험
Worker 하나당 메모리 비용탭이 많을 때 비용
모바일 Safari의 OPFS quota와 eviction 동작보존 기본값 검증
