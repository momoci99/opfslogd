벤치마크와 브라우저 확인

상태: 6단계 완료 · 최종 수정 2026-11-01 · 관련 결정: docs/decisions.md #058 ~ #060 (7단계에서 #064, #066 측정 항목 추가, 8단계에서 구현 단계 측정 일부 완료) · 코드: test/browser/, test/storage-check/, bench/, vitest.config.ts

설계가 기대는 브라우저 동작이 실제로 그런지 확인하고, 초안 숫자를 정할 속도를 잽니다. 각 문서의 "검증할 것" 항목의 결과는 이 문서에 모읍니다.

  2. 실행 방법
  3. 브라우저 API 확인 결과
  4. 속도 측정
  5. 구현 단계로 넘긴 것
  6. 실기기에서 직접 확인할 것

1. 범위

6단계는 라이브러리 코드 없이 데스크톱 브라우저 엔진 3종(Chromium, Firefox, WebKit)에서 확인할 수 있는 것만 다룹니다(#058).

  • 브라우저 API 확인: 설계가 가정한 동작이 되는지. 안 되면 설계가 바뀌므로 먼저 합니다.
  • 속도 측정: 라이브러리 없이 잴 수 있는 것.

Playwright의 WebKit은 Safari와 같지 않고, Playwright는 휴대폰에서 돌지 않습니다. Chromium의 CPU throttling도 저사양 휴대폰을 흉내 낼 뿐입니다. 그래서 모바일 수치는 실기기 확인으로 넘깁니다.

2. 실행 방법

pnpm exec playwright install chromium firefox webkit   # 처음 한 번
pnpm test                                              # unit + browser
pnpm vitest run --project browser --reporter=verbose   # 브라우저 결과만, 기록 줄 포함
pnpm check:bfcache                                     # bfcache 확인 (Chromium 창이 열림)
pnpm build && pnpm check:vite                       # Vite 앱에서 Worker 경로 확인 (가짜 패키지 + 실제 dist)
pnpm build && pnpm check:storage                    # 강제 종료 뒤 남는 쓰기, quota 초과 때 쓰기 (8단계)
node bench/run.mjs --only=firefox                      # bench를 한 엔진에서만
  • vitest.config.ts는 프로젝트 둘로 나뉩니다. unit은 jsdom에서 src/**/*.test.ts를, browser는 실제 브라우저에서 test/browser/**/*.test.ts를 돌립니다.
  • OPFS 작업은 테스트용 Worker(test/browser/opfs.worker.ts)가 합니다. 라이브러리처럼 Worker 안에서 sync access handle을 씁니다.
  • WebKit은 Playwright 기본 컨텍스트(일회용)에서 OPFS를 막습니다. navigator.storage.getDirectory()가 UnknownError를 던집니다. 그래서 WebKit만 영구 컨텍스트(node_modules/.cache/vitest-webkit-profile)로 돌리고, 영구 컨텍스트는 페이지를 하나만 열 수 있어서 파일을 하나씩 실행합니다.
  • CI도 같은 테스트를 돌립니다. 테스트 전에 브라우저 3종을 설치합니다.

3. 브라우저 API 확인 결과

측정 환경: Playwright 1.64.1 · Chromium 156 · Firefox 157 · WebKit 27.2 · macOS · 2026-11-01

항목ChromiumFirefoxWebKit설계에 미치는 영향
OPFS 안에서 FileSystemFileHandle.move()로 닫힌 세그먼트를 다른 디렉터리로 옮기기 (architecture) 됨됨됨 세그먼트 상태 전이(#012)를 그대로 둡니다. 테스트가 assert합니다.
다른 Worker가 sync access handle을 연 파일을 getFile()로 읽기 (architecture, api) 읽힘읽힘읽힘 다른 탭의 활성 세그먼트를 나중에 export에 넣을 수 있습니다(#054). 쓰는 도중에 읽으면 마지막 줄이 덜 쓰였을 수 있으므로, 읽는 쪽은 줄바꿈으로 끝나지 않는 마지막 줄을 건너뜁니다. 테스트는 결과만 기록합니다. 상대가 계속 쓰는 동안 읽는 경우(NotReadableError 가능성)는 확인하지 않았고, v0.1은 다른 탭의 활성 세그먼트를 계속 뺍니다(#054 메모).
Worker가 sync access handle을 연 페이지가 bfcache에 들어가는지, 돌아온 뒤 쓰기가 이어지는지 (protocol) 들어감, 쓰기 이어짐자동 확인 불가 → 실기기 Chromium에서는 우리 라이브러리가 사용자 앱의 bfcache를 끄지 않습니다. 돌아온 Worker는 같은 handle로 이어서 씁니다(#020).
Web Lock을 쥔 페이지가 bfcache에 들어가는지 (참고) 들어감자동 확인 불가 → 실기기 Lock은 실행할 때만 쥐므로(#022) 평소에는 해당이 없습니다. 참고로만 남깁니다.
npm으로 설치한 패키지가 new Worker(new URL('./worker.js', import.meta.url))로 Worker를 띄울 때 Vite 앱에서 되는지 (architecture) 됨 (Vite 8.3.5, Chromium) dev(설정 없음), dev(optimizeDeps.exclude), build + preview 모두 Worker가 뜨고 OPFS가 됩니다. 사용자에게 optimizeDeps.exclude를 요구할 필요가 없습니다(#009). 단, 아래 조건이 있습니다.

bfcache 확인 방법

Vitest browser mode는 테스트를 iframe 안에서 돌려서 페이지 이동을 볼 수 없습니다. 그래서 test/bfcache/run.mjs가 Playwright로 직접 확인합니다(pnpm check:bfcache, Chromium 창이 열립니다).

  • 페이지 A를 열고 경우별로 준비한 뒤, 페이지 B로 갔다가 뒤로 갑니다. A의 pageshow 이벤트에서 persisted가 true이면 bfcache에서 복원된 것입니다.
  • 경우: 빈 페이지(대조군), Worker만 있는 페이지, Worker가 sync handle을 연 페이지, Web Lock을 쥔 페이지
  • 대조군이 복원되지 않으면 그 브라우저 설정에서는 bfcache가 꺼진 것이므로 나머지 결과는 의미가 없습니다.
  • Playwright에서는 headed Chromium만 대조군이 복원됩니다. headless Chromium은 이유가 masked로만 나오고 복원되지 않습니다. Firefox는 bfcache pref를 켜면 뒤로 간 페이지가 다시 보이지 않습니다. WebKit은 headless와 headed 모두 대조군도 복원되지 않습니다. 그래서 Firefox와 Safari는 실기기에서 확인합니다.
  • Playwright는 Chromium에 --disable-back-forward-cache를 기본으로 넣으므로 스크립트가 이를 뺍니다. 복원된 페이지는 load 이벤트가 다시 발생하지 않으므로 goBack()은 commit까지만 기다립니다.
  • CI에서는 돌리지 않습니다. 창이 필요하기 때문입니다.

Vite 확인 방법과 조건

test/vite-dev/run.mjs(pnpm check:vite)가 가짜 패키지(test/vite-dev/fake-pkg)를 임시 Vite 앱의 node_modules에 복사해 넣고, 세 경우를 Chromium headless에서 엽니다. Worker는 자기가 어디서 로드됐는지와 OPFS가 되는지를 보고합니다. Vite는 Vitest가 의존하는 것을 그대로 씁니다.

8단계부터는 빌드한 실제 패키지(package.json + dist/)도 같은 방식으로 넣고, init() → logger.info() → flush() 뒤 OPFS 파일에서 레코드를 다시 읽습니다. dev와 build + preview 모두 됩니다(2026-11-01, Vite 8.3.5, Chromium). Worker와 메인이 함께 쓰는 코드가 별도 청크로 나뉘어도 문제없습니다.

  • 조건: Vite는 new Worker(new URL('./worker.js', import.meta.url), ...)가 한 식으로 쓰였을 때만 Worker로 알아봅니다. URL을 변수에 담아 new Worker(url)로 넘기면 dev에서는 되지만, build에서는 Worker 파일이 작은 에셋으로 취급되어 data: URL로 인라인되고 OPFS가 SecurityError: Storage directory access is denied로 막힙니다. 개발 중에는 보이지 않고 배포 후에만 드러납니다.
  • Vite 외 번들러(webpack, Rollup, esbuild 단독 등)는 아직 확인하지 않았습니다.

부수적으로 알게 된 것

  • WebKit의 일회용 컨텍스트에서 OPFS가 막힌다는 것은 실제 Safari 사설 브라우징에서도 getDirectory()가 실패할 가능성이 크다는 뜻입니다. 이 경우는 #041(저장소를 시작할 수 없으면 닫힌 logger처럼 동작)로 처리됩니다. 실제 Safari 확인은 실기기 목록에 둡니다.

4. 속도 측정

코드: bench/. 실행: pnpm bench(데스크톱 엔진에서 페이지를 열어 결과를 모음), pnpm bench:serve(LAN에 페이지를 열어 휴대폰으로 접속). Vitest의 bench는 browser mode에서 동작하지 않아(bench가 export되지 않음) 측정 코드를 직접 작성했습니다. 각 값은 약 50ms짜리 측정을 15번 해서 얻은 중앙값입니다.

측정 환경: Playwright 1.64.1 · Chromium 156 · Firefox 157 · WebKit 27.2 · macOS · 2026-11-01. "Chromium 4x"는 CPU를 4배 느리게 한 Chromium으로, 저사양 휴대폰을 흉내 낸 값일 뿐입니다.

레코드 크기: 작은 것 50바이트(msg만), 중간 184바이트(ctx에 키 5개), 큰 것 838바이트(ctx에 객체 10개 배열).

해석

  • #014 유지: log() 한 번의 직렬화는 중간 레코드 기준 1 µs 미만이고, Chromium 4x의 큰 레코드도 6.5 µs입니다. "평균 수 µs 이하" 목표 안에 듭니다.
  • #015 유지: 문자열 보관이 모든 엔진에서 encodeInto보다 2~10배 적게 듭니다. 호출마다 encodeInto를 부를 이유가 없습니다.
  • flush 한 번은 최대 약 1,400줄입니다. 크기 조건(256K자, #017) 때문에 폭주 때도 한 번에 2만 건이 쌓이지 않습니다. #042와 api.html의 "flush 한 번 약 2만 건"은 크기 조건이 생기기 전의 가정입니다. 256K자 flush 한 번의 join + encode는 Chromium 약 0.25ms, Chromium 4x 약 1ms입니다.
  • subscriber 비용 (#042): flush 한 번(약 1,400줄) 파싱은 Chromium 약 0.7ms, Chromium 4x 약 2.9ms입니다. 다만 100k/s 폭주가 1초 이어지면 합계가 Chromium 약 50ms, Chromium 4x 약 200ms로, 메인 스레드의 5~20%입니다. 디버깅용(#043)이라는 전제로는 받아들일 만합니다. 한 번에 파싱하는 방식은 줄마다 파싱하는 것보다 10~15%만 빠르므로, 줄마다 파싱해도 됩니다.
  • flush 주기와 1% 기준 (#017): 초당 1만 건에서 flush의 줄 수에 비례하는 비용은 Chromium 4x 기준 메인 스레드의 약 0.7%이고, 이 값은 주기와 상관이 없습니다. 주기를 정하는 것은 flush 한 번마다 고정으로 드는 비용(postMessage, 타이머, ack 처리)인데, 이것은 구현이 있어야 잴 수 있습니다(구현 단계). 참고로 같은 조건에서 log() 쪽 직렬화가 약 0.9%를 더 씁니다.
  • #016 유지: 프레임 없이 8MB 세그먼트를 스캔해도 Firefox 약 35ms, 나머지 7ms 안팎입니다. 보존 상한 50MB(#052) 전체를 export해도 Worker에서 1초 미만으로 예상됩니다. Firefox는 Blob.text()가 다른 엔진보다 5~10배 느립니다.

하지 않은 측정: JSON.stringify vs msgpackr (#016). 결과와 상관없이 런타임 의존성을 들이지 않고, 직렬화가 이미 목표 안이므로 뺐습니다(#060).

5. 구현 단계 측정

실제 쓰기 경로가 있어야 의미가 있는 측정입니다(#058). 8단계 단위 4(Worker 쓰기)까지의 코드로 잰 결과와, 메인 스레드 연결(단위 5) 뒤에 잴 것을 나눕니다.

확인ChromiumFirefoxWebKit설계에 미치는 영향
ack 받은 쓰기가 브라우저를 SIGKILL로 죽여도 남는지 (#074). 1,300줄 묶음 40개(11MB) 전부 남음전부 남음전부 남음 #074 유지. 쓰기마다 flush()할 필요가 없습니다. 기기 전원 차단은 확인하지 않았습니다.
용량이 찼을 때 sync handle write()의 동작 (#064) 예외 없음. 일부만 쓰고 엉뚱한 값(4294967288) 반환 예외 없음. 아무것도 쓰지 않고 0 반환 자동 확인 불가 → 실기기 QuotaExceededError가 오지 않습니다. 쓴 바이트 수가 다르면 용량 부족(quota)으로 보고 되돌립니다. Chromium은 일부를 쓰므로 #064의 되돌리기가 꼭 필요합니다.
같은 상황에서 라이브러리 Worker의 처리 ack ok: false, reason: "quota". 파일에는 온전한 줄만 남음(줄바꿈으로 끝남) — #064가 설계대로 동작합니다.

quota는 Chromium은 CDP Storage.overrideQuotaForOrigin(8MB)으로, Firefox는 dom.quotaManager.temporaryStorage.fixedLimit pref(50MB)로 낮췄습니다. WebKit은 Playwright에서 quota를 낮출 방법이 없습니다.

해석

  • #014 유지: 라이브러리의 log() 전체(거절 검사, 직렬화, 큐)가 중간 레코드 기준 1 µs 미만입니다. 거절된 호출은 수 ns로, 과부하 때 메인 스레드 부담이 거의 없습니다(#019).
  • #074 유지: 강제 종료에도 ack 받은 데이터가 모두 남았고, macOS 데스크톱에서는 쓰기마다 flush()해도 측정할 만한 차이가 없었습니다. 휴대폰의 flush() 비용은 다를 수 있으나, 내구성에 필요하지 않으므로 그대로 둡니다.
  • Worker 쓰기는 충분히 빠릅니다: 257KB 묶음 하나에 약 1ms이므로 초당 약 250MB를 쓸 수 있습니다. 목표 폭주(초당 10만 건, 약 20MB/s)의 10배 이상입니다.

메인 스레드 연결(단위 5) 뒤에 잴 것

  • flush 주기와 크기: 200ms, 256K자, error 뒤 50ms (#017). flush 한 번마다 드는 고정 비용(postMessage, 타이머, ack)을 재서 정합니다.
  • 폭주와 메인 스레드 긴 작업이 겹칠 때 버려지는 양, 80% 문턱과 4M자 상한 (#018, #019)
  • pagehide 때 보낸 flush가 파일에 쓰이는 비율 (#020)
  • flush마다 새 버퍼를 할당할 때의 GC 비용 (#015)
  • Worker 하나당 메모리
  • 로그가 많은 앱의 업로드 요청 빈도, 탭 여러 개일 때 retention 동작 (세그먼트 2MB, #066)

6. 실기기에서 직접 확인할 것

자동화가 어렵거나 실제 기기, 긴 시간이 필요한 항목입니다(#058).

  • 모바일 Safari의 OPFS quota와 eviction 동작
  • Safari(WebKit)에서 용량이 찼을 때 sync handle write()가 예외를 던지는지, 적게 썼다고 반환하는지 (#064). Chromium과 Firefox는 예외를 던지지 않습니다(결과)
  • Safari ITP 7일 상한이 OPFS 데이터를 지우는지 (#051)
  • Safari 사설 브라우징에서 getDirectory()가 실패하는지 (#041)
  • Firefox와 Safari(데스크톱, iOS)에서 Worker가 sync handle을 연 페이지가 bfcache에 들어가는지, 돌아온 뒤 쓰기가 이어지는지 (#020). test/bfcache/의 페이지를 열고 직접 뒤로 가기를 하면 됩니다.
  • Web Lock을 가진 탭이 freeze되는지, 브라우저별로 언제 되는지 (#022)
  • 느린 모바일 회선에서 2MB 세그먼트 업로드 시간 (#045, #066). 처음에는 8MB였음
  • 휴대폰에서 pnpm bench:serve 페이지 결과 (특히 저사양 Android, iOS Safari)
  • 장애 복구 직후 여러 클라이언트가 밀린 세그먼트를 한꺼번에 올릴 때의 부하 (#047)
